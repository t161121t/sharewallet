# マイグレーション履歴について

sharewallet は開発初期に SQLite を使用しており、途中で PostgreSQL(Supabase)へ移行しました。そのため、このディレクトリのマイグレーション履歴には移行前後で役割の異なるファイルが混在しています。読む際は以下を前提にしてください。

## 各マイグレーションの位置づけ

| マイグレーション | 位置づけ |
| --- | --- |
| `20260213144041_init` | **意図的な no-op**。SQLite 時代の初期マイグレーションだったが、PostgreSQL 移行時に内容が丸ごと `20260313000000_init_postgresql` に置き換えられたため、中身は説明コメントのみになっている。 |
| `20260227150405_core_features` | **意図的な no-op**。同上の理由で内容を置き換え済み。 |
| `20260313000000_init_postgresql` | **実質的なベースライン**。PostgreSQL 上のスキーマを最初から作り直す `CREATE TABLE` 群がここに入っている。新規環境をセットアップする場合、実質的にはここから始まっていると考えてよい。 |
| それ以降(`20260425170030_add_group_invitations` など) | 通常通りの追加マイグレーション。 |

## なぜ2つの no-op がそのまま残っているのか

Prisma Migrate は「適用済みマイグレーションの一覧(ファイル名がキー)」を DB 側の `_prisma_migrations` テーブルで管理しています。本番 Supabase DB には `20260213144041_init` と `20260227150405_core_features` が(SQLite 時代の内容で)**既に適用済みとして記録されています**。

このため、これらのマイグレーションフォルダを削除・リネームしたり、履歴を圧縮(squash)したりすると、本番DBの`_prisma_migrations`テーブルが記録している名前と、リポジトリ上のフォルダ名が一致しなくなり、`prisma migrate deploy` が「適用したはずのマイグレーションが見つからない」と判断してエラーになる、あるいは意図せず再適用しようとするリスクがあります。読みやすさのために履歴を書き換えるより、**「意図的な no-op である」という事実をドキュメント化して残す**方を選びました(詳細は `docs/30-Prismaマイグレーション履歴の整理まとめ.md` を参照)。

## 新しいマイグレーションを追加するときの注意

- 通常通り `prisma migrate dev`(ローカル)や、このリポジトリの運用に合わせた手順でマイグレーションを追加してください。過去の no-op を気にする必要はありません。
- 上記2つの no-op ファイルは**今後も変更・削除しないでください**。本番DBの適用履歴と一致しなくなります。
