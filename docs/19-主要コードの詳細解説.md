## 1. `src/lib/apiClient.ts` — ブラウザと API の接点

**役割**：`fetch` の重複を避け、**Bearer 付与・JSON・エラー整形・localStorage 操作** を 1 か所に集約する。

| ブロック | 行付近 | 何をしているか |
| --- | --- | --- |
| `getToken` / `setToken` / `clearToken` | 24〜39 | `sharewallet_token` キーで JWT を読み書き。`typeof window === "undefined"` は **SSR やサーババンドルで `localStorage` に触れない** ためのガード（呼び出し側がクライアントでも、import だけで落ちるのを防ぐ）。 |
| `getSelectedGroupId` 系 | 47〜62 | 支出画面などで「前回選んだグループ」を復元するための永続化。トークンと独立したキーにしているので、ログアウト時は `logout()` でまとめて消せる。 |
| `getCachedUser` / `setCachedUser` | 66〜87 | `sharewallet_user` に `UserProfile` の JSON を保存。`JSON.parse` は `try/catch` で囲み、**壊れた JSON が入っていてもアプリ全体を落とさない**。 |
| `ApiClientError` | 91〜99 | HTTP ステータスとメッセージを保持する **専用エラー型**。UI 側で `instanceof ApiClientError` や `status` を見てトースト文言を分岐しやすい（現状はシンプルに `message` を表示している画面も多い）。 |
| `apiFetch` | 101〜126 | (1) `getToken()` でトークン取得 → (2) `Content-Type: application/json` をデフォルト付与 → (3) トークンがあれば `Authorization: Bearer ...` を付与 → (4) `fetch` 実行 → (5) `!res.ok` のとき本文を `json()` で読み、`ApiClientError` を throw。失敗時の JSON が取れない場合は `{ error: "不明なエラー" }` にフォールバック。 |
| `login` | 130〜144 | API が返した `token` と `user` を **クライアント側で即座に永続化**。サーバは Cookie をセットしないため、**ログイン成功後の状態はこの 2 行が真実**になる。 |
| `register` | 146〜155 | 登録 API だけを叩き、**トークンは保存しない**（登録直後はログイン画面へ誘導する UX のため）。 |
| `logout` | 158〜162 | トークン・ユーザーキャッシュ・選択グループを一括削除し、**クライアント上の認証状態を完全に無効化**。 |
| `updateMe` | 170〜181 | PUT のレスポンスで `setCachedUser` し、**プロフィール編集後もキャッシュと UI が矛盾しない**ようにしている。 |
| 各 `get*` / `create*` | 以降 | URL はすべて **相対パス**（`/api/...`）。同一オリジン前提で、環境ごとのベース URL を持たないシンプル構成。 |

**データの流れ（例：支出一覧）**：画面が `getExpenses(groupId)` を呼ぶ → `apiFetch` が Bearer 付き GET → Route Handler が Prisma で取得 → JSON が `ExpenseRecord[]` としてパースされて返る。

## 2. `src/lib/auth.ts` — JWT とグループ認可の共通部品

| シンボル | 内容の詳細 |
| --- | --- |
| `SECRET` / `ALG` | `JWT_SECRET` を `TextEncoder` で **バイト列**にし、`jose` の HS256 に渡す。環境変数未設定時は開発用の固定文字列（本番では必ず上書きすべき）。 |
| `createToken` | `sub`（subject）クレームに **ユーザーの主キー（cuid）** を載せ、`iat`（発行時刻）と `exp`（7 日）をセットして署名。ペイロードは最小限にし、**個人情報やロールを JWT に載せない**（改ざんされたときの影響範囲を小さくする）。 |
| `verifyToken` | `jwtVerify` が失敗したら **例外ではなく `null`** を返す設計。Route 層では「未ログイン」と「期限切れ」を区別せずまとめて扱える。 |
| `getAuthUserId` | `Authorization` ヘッダが `Bearer ` で始まる場合だけトークン文字列を `slice(7)` で取り出し検証。**スキーム名の大文字小文字や余分な空白は厳密には許容していない**（シンプルさ優先）。 |
| `requireAuthUserId` | `getAuthUserId` が falsy なら `throw new Error("UNAUTHORIZED")`。Route の `catch` で **HTTP 401 にマッピング**するための識別子。 |
| `getGroupMember` | Prisma の **複合ユニーク** `userId_groupId` で 1 行取得。存在しなければ `null`。 |
| `assertGroupMember` | メンバーでなければ `FORBIDDEN`。**「グループの存在」ではなく「参加しているか」** を先に見るため、存在しない `groupId` でも 403 になり得る（情報リークを抑える意図にもなる）。 |
| `assertGroupRole` | メンバー確認のあと、`member.role` が `allowedRoles` に含まれるか検証。**OWNER 専用操作**はここを `[GroupRole.OWNER]` で呼ぶ。 |

## 4. `src/lib/settlement.ts` — 残高計算と minimum cash flow

**入力**：`GroupMember[]`（精算対象メンバー）、`ExpenseRecord[]`（各支出の支払者・シェア）。

**ステップ 1 — `balanceMap` の初期化（13〜14 行付近）**  
全メンバー ID をキーにした `Map` を 0 で埋める。以降、ここに **「正なら受け取りたい、負なら払いたい」正味額** を累積する。

**ステップ 2 — 支出ループ（16〜29 行付近）**  
各支出について：

1. `memberId`（実際の支払者）の残高に **`+amount`**。現金を立て替えた人はその分プラス。
2. `shares` があれば、各シェアについて **`owed = amount * (percent / 100)`** をその `userId` の残高から **減算**（負担分）。
3. `shares` が空のときは **均等割りフォールバック**：`amount / members.length` を全員から引く。API 側では常に `ExpenseShare` を作るが、**このライブラリ単体でも入力揺れに耐える**ようにしてある。

**ステップ 3 — `memberBalances`（32〜38 行付近）**  
`Map` の値を `Math.round` し、表示用の `MemberBalance[]` に整形。浮動小数の `%` 計算の末端ノイズを整数円に寄せる。

**ステップ 4 — `minimumCashFlow`（48〜84 行付近）**  
債権者（`balance > 0`）と債務者（`balance < 0`）を **絶対値の大きい順**にソート。二つのポインタ `i`, `j` で、常に最大債権者と最大債務者の間で **`Math.min` の金額だけ送金**を記録し、両者の残高を減らす。どちらかが 0 になったらポインタを進める。**ループ回数は高々メンバー数程度**で終わる。

**`settlement/route.ts` との接続**：DB から取得した `groupData.members` を `GroupMember[]` に、`expenses` を `ExpenseRecord[]` に写経し、`calculateSettlement` に渡す。`memberName` を空文字にしているのは **精算計算に名前は不要**だから（トランザクション表示用の名前は `minimumCashFlow` 内で `MemberBalance` から再取得している）。

## 5. `src/app/api/groups/[groupId]/expenses/route.ts` — 支出の GET / POST

**GET（7〜59 行付近）**

1. `requireAuthUserId` → `assertGroupMember` の順で **認証→そのグループのメンバーか** を確認。
2. `prisma.expense.findMany` で `groupId` 一致の支出を、`member` と `shares.user` を `include`。`orderBy: { date: "desc" }` で **新しい支出が先頭**。
3. `map` で `ExpenseRecord` 形に正規化。`category` は DB の文字列を `as ExpenseRecord["category"]` で型付け（**実行時バリデーションは別途ない**点に注意）。
4. `catch` で `UNAUTHORIZED` / `FORBIDDEN` / その他を分岐し、**日本語の `error` メッセージ**とステータスを返す。

**POST（63〜165 行付近）**

1. 同様に認証・認可。
2. `req.json().catch(() => null)` で **不正 JSON や空ボディを null 化**し、400 で返す。
3. `members` を再取得し `memberIds` を `Set` に。**シェアに含められる userId は参加メンバーに限定**するためのルックアップ。
4. `incomingShares`：`body.shares` が配列で長さ 1 以上ならそのまま、**さもなければ均等割り** `{ userId, percent: 100 / members.length }` を全員分生成。ここで **「未指定＝均等」がデータとして固定化**される。
5. `percentTotal` が 100±0.01 か検証。`Number(s.percent || 0)` のように **`percent` が欠ける・文字列でも数値化**できるようにして合算している。
6. 各シェアについて `memberIds.has` と `percent >= 0` を検証。
7. `payerId = body.memberId ?? userId`：**誰が払ったか未指定ならログインユーザーが支払者**。
8. `prisma.expense.create` の nested `shares: { create: [...] }` で **支出とシェアを同一トランザクション相当で作成**。
9. 201 とともに、GET と同形の `ExpenseRecord` を返す（クライアントが再フェッチしなくてよい）。

## 6. `src/app/api/dashboard/summary/route.ts` — 個人ダッシュボード集計

1. `requireAuthUserId` のみ（**グループ横断**なので `assertGroupMember` は不要）。
2. `periodFrom` / `periodTo` を **`Date(y, m, 1)` 方式**で算出。ローカルタイムゾーン（サーバの TZ）基準の月境界。Vercel 上は **UTC に固定されない**点を理解しておく必要がある（改善の議論は [18章 §6.6](./18-なぜそう実装したのか.md) と関連）。
3. `expenses` の `where`：`memberId: userId` かつ期間内かつ **`group.members` に自分が含まれるグループの支出だけ**。**脱退済みグループの古いデータを集計から外す**効果がある。
4. `previousMonthAggregate` は `aggregate` の `_sum` で **先月の合計だけを DB に任せて取得**（一覧を引かずに済む）。
5. `for` ループで `groupMap` / `categoryMap` を更新。`normalizeCategory` で **旧ラベルを現行 `CategoryName` に寄せる**。
6. `byGroup` / `byCategory` は金額降順ソートし、`DashboardSummary` として返却。

## 7. `src/app/api/auth/login/route.ts` / `register/route.ts`

**login**

1. ボディ必須チェック（email / password）。
2. `findUnique({ where: { email } })` でユーザーを取得。**ユーザー不存在とパスワード不一致を同一メッセージで返す**（タイミング攻撃対策としては弱いが、列挙耐性は意識した一般的パターン）。
3. `bcrypt.compare(平文, passwordHash)` で検証。
4. `createToken(user.id)` で JWT を発行し、`LoginResponse` 型どおり返す。

**register**

1. 名前・メール・パスワードの必須チェック。
2. メール重複は **409 Conflict**。
3. `bcrypt.hash(..., 10)` でコスト因子 10 のハッシュを生成して保存。
4. 返却は `user` のみ（**トークンなし**）。クライアントは登録後にログイン API を叩くか、ログイン画面へ遷移する。

## 8. `src/app/api/groups/route.ts` — グループ作成と `iconUrl` フォールバック

**POST の要点（61 行以降）**

1. `body.name` を trim し、必須検証。`color` は **正規表現で `#` + 6 桁 hex** のときだけ採用。**さもなければ**デフォルトのブランド色 `#c9a227`。
2. `iconUrl` は文字列ならそのまま、**さもなければ** `null`。
3. 外側 `try` で `prisma.group.create` に `iconUrl` を含めて実行。
4. 失敗時、`isUnknownIconUrlError(e)` が真なら **`iconUrl` なしで再試行**。Prisma の「未知の引数」と SQLite/Postgres の「カラムなし」の両方のメッセージ文字列を見ている（理由の整理は [18章 §6.5](./18-なぜそう実装したのか.md)）。
5. 成功した `created` を `Group` 型の DTO に写して返す。
