# 26. 支出フィルタリング機能実装まとめ

## これは何のドキュメント？

[GitHub issue #33](https://github.com/t161121t/sharewallet/issues/33) で行った、支出履歴画面(`src/app/expense/history/page.tsx`)への期間・カテゴリ・メンバーによる絞り込み機能の実装記録です。

## まず結論（今回できたこと）

- `GET /api/groups/[groupId]/expenses` がクエリパラメータ `?from=&to=&category=&memberId=` を受け付け、DB側(Prisma `where`句)で絞り込むようになった
- 支出履歴画面に「すべて/今月/先月/カスタム範囲」の期間タブ、カテゴリ選択、メンバー選択のUIを追加した
- クエリパラメータなしでの挙動は完全に従来通り(全件取得)

```bash
npx tsc --noEmit   # 型エラーなし
npx vitest run     # Test Files 4 passed / Tests 42 passed(新規6件を含む)
```

---

## 背景 — なぜこの変更が必要だったか

支出履歴画面は取得した支出を日付でグループ化して全件表示するだけで、絞り込み手段がありませんでした。支出件数が増えると「先月の食費だけ見たい」「特定のメンバーの支出だけ確認したい」といった用途に対応できず、一覧が長くなるほど目的の支出を探しにくくなります。issue #33 として、期間・カテゴリ・メンバーでの絞り込みが要望されました。

---

## 目的

### 主目的

1. サーバー側(DB)で絞り込むことで、件数が増えても表示側の負荷を増やさない
2. 既存の全件取得の挙動をクエリパラメータなしの場合は完全に維持する(後方互換)
3. 既存のUI部品・データ取得済みの情報(`group.members`)を再利用し、新しい依存を増やさない

### あえてやらなかったこと

| やらなかったこと | 理由 |
| --- | --- |
| 月別・年別の集計表示 | issue #34の別スコープ。今回は「絞り込んで一覧表示」のみ |
| ページコンポーネントのフック分割 | issue #27の別スコープ。フィルタ用のstateはこのページに直接追加した |
| zodによる厳密なクエリパラメータバリデーション | issue #23の別スコープ。今回は「不正な値は無視してフィルタなし扱い」という軽量な方針に留めた |
| 無限スクロール/ページネーション | issue #36の別スコープ |

## 何を実装したか

### 1. API側 — `src/app/api/groups/[groupId]/expenses/route.ts`

`parseExpenseFilters()` でクエリパラメータから Prisma の `where` 句を組み立てます。

```ts
function parseExpenseFilters(searchParams: URLSearchParams) {
  const where: { date?: { gte?: Date; lt?: Date }; category?: CategoryName; memberId?: string } = {};
  // from/to → date.gte / date.lt (to は「その日を含む」ため翌日0時未満で絞り込む)
  // category → 既知の11種類のいずれかの場合のみ適用
  // memberId → そのまま適用
  return where;
}
```

**不正な値の扱い**: 不正な日付文字列や未知のカテゴリ名は「絞り込みなし」として無視します。フィルタは補助的な機能であり、不正入力のたびに400エラーを返すよりは全件表示にフォールバックする方が自然だと判断しました(検索フォームでよくある「該当なしなら空、条件がおかしければ無視」という一般的なUXパターンに合わせています)。

**`to`の扱い**: `to=2026-01-31`は「1月31日を含む」ことを意味するため、内部的には`lt: 2026-02-01T00:00:00`(翌日0時未満)に変換しています。単純に`lte: 2026-01-31T00:00:00`にすると、時刻情報を持つ`date`カラムの値(例: 1月31日15:00)が範囲外になってしまうためです。

### 2. `src/lib/apiClient.ts` — `getExpenses()`の拡張

```ts
export type ExpenseFilters = {
  from?: string; to?: string; category?: CategoryName; memberId?: string;
};

export async function getExpenses(groupId: string, filters?: ExpenseFilters) {
  const query = new URLSearchParams();
  // filtersの各項目をquery paramへ変換
  return apiFetch<ExpenseRecord[]>(`/api/groups/${groupId}/expenses${qs ? `?${qs}` : ""}`);
}
```

第2引数を省略した場合は従来通りクエリパラメータなしでリクエストされ、挙動は完全に変わりません。

### 3. フロントエンド — `src/app/expense/history/page.tsx`

- 期間タブ(すべて/今月/先月/カスタム範囲)、カテゴリ選択(既存の`GenreSelect`コンポーネントを再利用)、メンバー選択(`group.members`から動的生成)を追加
- フィルタ用のstateを追加し、変更されたら`getExpenses(groupId, filters)`を再実行する`useEffect`を追加。**初回マウント時は既存のPromise.allによる全件取得と重複しないよう、`isFirstFilterRun`という参照でスキップしています**
- 今月/先月の期間計算は、`src/app/api/dashboard/summary/route.ts`に既にあった`new Date(y, m, 1)`パターンを踏襲しました

## よくある質問

### Q. なぜクエリパラメータのバリデーションにzodを使わなかったの？

issue #23(zodによるスキーマバリデーション導入)は別issueとしてスコープ化されています。今回は既存のコードベースの他ルートと同じ「手書きの軽量チェック」のスタイルに合わせ、スコープを絞りました。

### Q. カテゴリの選択に既存の`GenreSelect`を再利用した理由は？

支出登録フォーム(`src/app/expense/page.tsx`)と全く同じカテゴリ一覧・見た目になり、UIの一貫性が保てるためです。新しいコンポーネントを増やすと保守対象が増えてしまいます。

### Q. 期間フィルタを「先月」にしたときの月末日の扱いは？

`new Date(y, m, 0)`はJavaScriptの仕様で「その月の最終日」を返すため(例: `new Date(2026, 2, 0)`は2026年2月28日)、これを使って月末日を算出しています。
