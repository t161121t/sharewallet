## 0. 全体の流れを1枚で

ブラウザがボタンを押してから DB に書き込まれるまで、データは必ず次の順で流れます。

```
ブラウザ（React コンポーネント）
   ↓ fetch()
src/lib/apiClient.ts          ← APIを呼ぶ窓口（トークン付与など）
   ↓ HTTP リクエスト
src/app/api/**/route.ts       ← Route Handler（受付係）
   ↓ 関数呼び出し
src/lib/auth.ts                ← 認証・権限チェック
   ↓ 関数呼び出し
src/lib/prisma.ts → Prisma Client ← DBとの会話係（ORM）
   ↓ SQL
PostgreSQL（Supabase）
```

このガイドでは上から順に、各層で何が起きているかを説明します。

### 0.1 矢印を1本ずつ実機で追う

上の図の「↓」を、実際に `curl -v` でキャプチャした本物の通信ログを使って1本ずつ分解します（ログインAPIを例にしています）。

#### ① ブラウザ → `fetch()`

画面側のコード（例: `src/app/login/page.tsx`）が `login(email, password)` を呼ぶと、最終的に `apiClient.ts` の中で次が実行されます。

```ts
// src/lib/apiClient.ts:116
const res = await fetch(path, { ...options, headers });
```

`fetch()` はブラウザ内蔵のネットワーク機能で、呼び出された瞬間に裏側で次が起きます。

1. URLからホスト名を解決（今回は `localhost` なので即解決。本番ではDNSルックップが入る）
2. 既存のTCP接続が使い回せるか確認（無ければ3-way handshakeで新規接続。今回は同一プロセスへの2回目以降の呼び出しなので**接続は再利用**される）
3. リクエスト内容をHTTP/1.1のテキスト形式に変換して送信

実際に流れているバイト列を`curl -v`で覗くとこうなっています（ヘッダー名はcurlの自動付与分も含む）。

```
POST /api/auth/login HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Content-Length: 55

{"email":"tanaka@example.com","password":"password123"}
```

`Content-Length: 55` は**ボディの文字列が何バイトかをブラウザ（fetch実装）が自動計算して付与**したものです。これがないと、サーバーは「ボディがどこで終わるか」を知る方法がありません。

#### ② `apiClient.ts` が「窓口」としてやっていること

`apiFetch<T>()`（`src/lib/apiClient.ts:102`）は、すべてのAPI呼び出しが必ず通る共通関数です。実際の処理順を分解すると：

```ts
async function apiFetch<T>(path: string, options: RequestInit = {}): Promise<T> {
  const token = getToken();                          // ① localStorageからJWTを読む（無ければnull）
  const headers: Record<string, string> = {
    "Content-Type": "application/json",
    ...(options.headers as Record<string, string>),
  };
  if (token) {
    headers["Authorization"] = `Bearer ${token}`;     // ② トークンがあれば自動で全リクエストに付与
  }
  const res = await fetch(path, { ...options, headers }); // ③ 実際の送信
  if (!res.ok) {
    const body = await res.json().catch(() => ({ error: "不明なエラー" }));
    throw new ApiClientError(res.status, body.error ?? "不明なエラー"); // ④ 失敗時は例外に変換
  }
  return res.json() as Promise<T>;                    // ⑤ 成功時はJSONをパースして返す
}
```

**ログイン呼び出し1回目はトークンがまだ無い**ので①で`null`、②はスキップされ`Authorization`ヘッダーは付きません（実際の`curl -v`ログにも`Authorization`は出ていません）。ログイン成功後、`login()`関数（`apiClient.ts:131`）が`setToken(data.token)`で初めてトークンを保存し、**次のリクエストから②が効くようになります**。

この「成功/失敗の分岐をここに1か所だけ書く」設計のおかげで、各画面のコードは`try { await getExpenses(...) } catch (e) { toast.error(e.message) }`のように**「成功した場合だけ」を素直に書ける**ようになっています（失敗時のステータスコード判定などを画面側で繰り返さなくていい）。

#### ③ サーバーが返すHTTPレスポンスの実物

サーバー側の`NextResponse.json(...)`（Route Handler内）が返したものを、再び`curl -v`で受信側として覗くとこうなっています。

```
HTTP/1.1 200 OK
content-type: application/json
vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

{"token":"eyJhbGciOiJIUzI1NiJ9...","user":{"id":"cmmp5ufpc...","name":"田中 太郎",...}}
```

- **`Transfer-Encoding: chunked`**: レスポンスボディを「全部できてから送る」のではなく「できた分から少しずつ送る」方式。サーバー側が事前に正確なバイト数を計算しない（できない）場合にこちらが使われます。小さいJSONでも、Next.jsの開発サーバーの内部処理（ミドルウェア層を経由してストリーミングする実装）によりこちらが選ばれています。
- **`vary: rsc, next-router-state-tree, ...`**: Next.jsのApp Routerが「同じURLでも、通常のfetchとRSC（React Server Components）的なナビゲーションでは返す内容が違う場合がある」ことをキャッシュ層に伝えるためのヘッダー。API Route自体はRSCを返しませんが、Next.jsのレスポンス処理パイプラインを通る以上、共通でこのヘッダーが付与されます。
- **`Connection: keep-alive` / `Keep-Alive: timeout=5`**: このTCP接続を5秒間維持し、次のリクエスト（例: ログイン直後に飛ぶ`/api/groups`など）が来たら**新しい接続を張らずに再利用**することをブラウザに伝えています。①で触れた「接続の再利用」がここで成立しています。

#### ④ ブラウザが受け取ってから画面に反映されるまで

`apiFetch`の`return res.json()`が解決すると、呼び出し元の`login()`がその値を受け取り、

```ts
// src/lib/apiClient.ts:141
setToken(data.token);       // localStorageに書き込み（同期処理・数ms）
setCachedUser(data.user);   // 同上
```

を実行してから`handleLogin()`（`login/page.tsx`）に値が返り、`router.push("/dashboard")`が呼ばれて画面遷移が起きます。**この一連の流れはすべて1つの`async`関数の中で順番に実行される**ため、「トークンが保存される前に画面遷移してしまう」ような競合は起きない設計です。



### 1.1 パスワードはどう守られているか — bcrypt

パスワードを **そのままDBに保存するのは絶対にNG**（DBが流出したら全員のパスワードが漏れる）。
そこで `bcrypt` という**ハッシュ関数**を使い、元のパスワードに戻せない文字列に変換してから保存します。

```ts
// src/app/api/auth/register/route.ts （新規登録時）
const passwordHash = await bcrypt.hash(body.password, 10);
```

- `10` は「ソルトラウンド数」。数字が大きいほど計算に時間がかかり、総当たり攻撃に強くなる（その分サーバーの負荷も増える）。
- ログイン時は逆算せず、**「入力されたパスワードを同じ方法でハッシュ化し、DBの値と一致するか」**を比較します。

```ts
// src/app/api/auth/login/route.ts:21
if (!user || !(await bcrypt.compare(body.password, user.passwordHash))) {
  // 一致しない → 401
}
```

`bcrypt.compare` の中で同じソルトを使って再計算し、結果を比較しています。これにより「ハッシュ化された値からパスワードを復元する」ことなく認証できます。

### 1.2 ログイン状態をどう維持するか — JWT

HTTPは**毎リクエストが独立**しています（サーバーは「さっき誰がログインしたか」を覚えていない）。
そこで、ログイン成功時に**「私はこのユーザーです」と証明できるトークン**を発行し、以後のリクエストにそのトークンを添えてもらう方式（JWT = JSON Web Token）を採用しています。

```ts 

// src/lib/auth.ts:12
export async function createToken(userId: string): Promise<string> {
  return new SignJWT({ sub: userId })       // payload に userId を埋め込む
    .setProtectedHeader({ alg: "HS256" })   // 署名アルゴリズム
    .setIssuedAt()                          // 発行時刻
    .setExpirationTime("7d")                // 7日で失効
    .sign(SECRET);                          // 秘密鍵で署名
}
```

JWTは3つの部分（ヘッダー.ペイロード.署名）からなる文字列です。**ペイロード自体は誰でも読めます**（base64エンコードだけで暗号化ではない）が、**署名があるおかげで改ざんはできません**。サーバーは `SECRET`（`JWT_SECRET`環境変数）を持っている自分だけが、正しい署名を作れることを利用して検証します。

```ts
// src/lib/auth.ts:21
export async function verifyToken(token: string): Promise<string | null> {
  try {
    const { payload } = await jwtVerify(token, SECRET); // 署名チェック＋有効期限チェック
    return (payload.sub as string) ?? null;
  } catch {
    return null; // 署名不一致・期限切れなどは全部 null
  }
}
```

フロント側は `localStorage` にトークンを保存し（`src/lib/apiClient.ts`）、毎リクエストで `Authorization: Bearer <token>` ヘッダーに載せて送ります。

```ts
// src/lib/auth.ts:31
export async function getAuthUserId(req: NextRequest): Promise<string | null> {
  const auth = req.headers.get("authorization");
  if (!auth?.startsWith("Bearer ")) return null;
  const token = auth.slice(7);              // "Bearer " の7文字を取り除く
  return verifyToken(token);
}
```

**ポイント**: JWTは「サーバーがセッションを覚えておかなくていい（ステートレス）」のが利点。一方、発行したトークンを途中で無効化する仕組みは無い（ログアウトはクライアント側でトークンを消すだけ）という弱点も持っています。

## 2. 認可（Authorization）— 「あなたは何をしていい？」を確認する

認証（誰か）が済んでも、**そのグループの支出を見ていいか／編集していいか**は別の問題です。これを担うのが認可（RBAC = Role-Based Access Control）です。

```ts
// src/lib/auth.ts:54
export async function assertGroupMember(groupId: string, userId: string) {
  const member = await getGroupMember(groupId, userId);
  if (!member) throw new Error("FORBIDDEN"); // グループに属していない
  return member;
}

// src/lib/auth.ts:62
export async function assertGroupRole(
  groupId: string, userId: string, allowedRoles: GroupRole[]
) {
  const member = await assertGroupMember(groupId, userId);
  if (!allowedRoles.includes(member.role)) throw new Error("FORBIDDEN");
  return member;
}
```

`GroupRole` は `OWNER` / `ADMIN` / `MEMBER` の3段階（`prisma/schema.prisma:13`）。すべての Route Handler は実行前に必ず次の順でチェックします。

```
requireAuthUserId()   → 「誰か」が分からなければ 401
assertGroupMember()   → 「そのグループに属しているか」でなければ 403
assertGroupRole()     → 「そのロールに権限があるか」（必要な場合のみ）
```

この**「認証 → 認可 → 業務処理」の順番を絶対に崩さない**のが、このコードベース全体の規約です（[`19-主要コードの詳細解説.md`](./19-主要コードの詳細解説.md) にも詳細あり）。

## 3. ORM（Prisma）— SQLを直接書かずにDBを操作する

### 3.1 ORMとは何か

ORM（Object-Relational Mapping）は、**SQLを直接書く代わりに、プログラミング言語のオブジェクト操作でDBを扱える**ようにするツールです。Prismaの場合、`prisma/schema.prisma` にモデルを定義すると、それに対応するTypeScriptの型と関数が自動生成されます。

```prisma
// prisma/schema.prisma:71
model Expense {
  id        String   @id @default(cuid())
  groupId   String   @map("group_id")
  memberId  String   @map("member_id")
  category  String
  amount    Int
  memo      String?
  date      DateTime
  ...
  shares ExpenseShare[]
  @@map("expenses")
}
```

これを書くだけで、以下のような操作がSQLなしで可能になります。

```ts
await prisma.expense.findMany({ where: { groupId } });
await prisma.expense.create({ data: { ... } });
```

裏側では Prisma が自動的に `SELECT * FROM expenses WHERE group_id = $1` のようなSQLを生成して実行しています。

### 3.2 `@map` の役割 — 命名規則の橋渡し

```prisma
passwordHash String @map("password_hash")
```

- コード側（TypeScript）は `camelCase`（`passwordHash`）
- DB側（PostgreSQLの慣習）は `snake_case`（`password_hash`）

`@map` を使うことで、**両方の言語のベストプラクティスを犠牲にせず両立**させています。

### 3.3 リレーション（テーブル同士のつながり）

```prisma
model ExpenseShare {
  expenseId String @map("expense_id")
  userId    String @map("user_id")
  percent   Float
  expense Expense @relation(fields: [expenseId], references: [id], onDelete: Cascade)
  user    User    @relation(fields: [userId], references: [id], onDelete: Cascade)
  @@unique([expenseId, userId])
}
```

- `@relation` は外部キー（FK）を表す。「`ExpenseShare.expenseId` は `Expense.id` を指す」という制約。
- `onDelete: Cascade` は「親（`Expense`）が消えたら、子（`ExpenseShare`）も自動で消える」という設定。グループを消したら関連する支出も配分も自動的に消える、というデータ整合性をDBレベルで保証しています。
- `@@unique([expenseId, userId])` は「同じ支出に同じユーザーの配分行が2つできない」という複合ユニーク制約。

`include` を使うとリレーションを一緒に取得できます（SQLの `JOIN` に相当）。

```ts
// src/app/api/groups/[groupId]/expenses/route.ts（GET）
const expenses = await prisma.expense.findMany({
  where: { groupId },
  include: {
    member: { select: { id: true, name: true, avatarUrl: true } },
    shares: { include: { user: { select: { id: true, name: true } } } },
  },
});
```

### 3.4 マイグレーション — スキーマ変更を履歴で管理する

`schema.prisma` を直接書き換えても、DBの実テーブルは自動で変わりません。`prisma migrate` コマンドで「変更内容をSQLファイル化して、DBに適用する」操作が必要です。

```
prisma/migrations/
├── 20260213144041_init/                    # 最初のテーブル群
├── 20260227150405_core_features/           # グループ・支出機能の追加
└── 20260313000000_init_postgresql/         # SQLite→PostgreSQL移行
```

各フォルダには実行されたSQLがそのまま残っており、「いつ、どのカラムが、なぜ追加されたか」をコードの変更履歴として追跡できます。

## 4. API設計 — Route Handlerの書き方

Next.js の **Route Handler**（`src/app/api/**/route.ts`）は、ファイルパスがそのままURLになる仕組みです（`app/api/groups/[groupId]/expenses/route.ts` → `/api/groups/:groupId/expenses`）。

### 4.1 1つのファイルに POST / GET を共存させる

```ts
export async function GET(req: NextRequest, { params }) { ... }
export async function POST(req: NextRequest, { params }) { ... }
```

同じファイル内でHTTPメソッドごとに関数を分けるのがNext.jsのルールです。`[groupId]` のような `[ ]` 付きフォルダは**動的パラメータ**で、`params` から非同期で取得します（`const { groupId } = await params;`）。

### 4.2 エラーハンドリングの型

このコードベースでは、**業務エラーを `throw new Error("文字列")` で表現し、一番外側の `catch` でHTTPステータスに変換する**という統一パターンを使っています。

```ts
try {
  const userId = await requireAuthUserId(req);  // 失敗時 throw "UNAUTHORIZED"
  await assertGroupMember(groupId, userId);     // 失敗時 throw "FORBIDDEN"
  // ここまで来たら認証・権限OK。業務処理を実行
  ...
} catch (e) {
  if (e instanceof Error && e.message === "UNAUTHORIZED") return 401で返す;
  if (e instanceof Error && e.message === "FORBIDDEN")    return 403で返す;
  return 500で返す; // 想定外のエラー（DB接続失敗など）
}
```

**なぜこの形にするのか**: `if (!isAuth) return 401` を全Routeに毎回書くと条件分岐が深くネストして読みにくくなります。代わりに「正常系だけを直線的に書き、異常系は例外で外に飛ばす」ことで、本来の業務ロジック（支出を登録する処理）が読みやすくなります。

### 4.3 バリデーション（入力検証）の例

`POST /api/groups/[groupId]/expenses` では、**「配分比率の合計が100%か」「配分先が本当にグループメンバーか」**をDBに保存する前にコードで検証しています。

```ts
const percentTotal = incomingShares.reduce((sum, s) => sum + Number(s.percent || 0), 0);
if (Math.abs(percentTotal - 100) > 0.01) {
  // 100にならない → 400 Bad Request
}
if (incomingShares.some((s) => !memberIds.has(s.userId) || s.percent < 0)) {
  // グループ外のユーザーが含まれる、または負の値 → 400
}
```

`Math.abs(percentTotal - 100) > 0.01` のように**完全一致ではなく誤差を許容**しているのは、`Float`（浮動小数点数）の計算が `33.33 + 33.33 + 33.34 = 100.00000000000001` のように微妙にずれることがあるためです。これは「浮動小数点誤差」と呼ばれる、コンピュータが小数を二進数で近似計算することによる典型的な問題です。

### 4.4 DTO変換 — DBの形とAPIレスポンスの形を分ける

Prismaが返すオブジェクトをそのままレスポンスにせず、**`src/types/index.ts` で定義した型に変換**してから返します。

```ts
const result: ExpenseRecord = {
  id: expense.id,
  category: expense.category as ExpenseRecord["category"],
  amount: expense.amount,
  memberId: expense.member.id,
  memberName: expense.member.name,
  memberAvatarUrl: expense.member.avatarUrl ?? undefined, // null → undefined に統一
  ...
};
```

`?? undefined` の変換が地味に重要です。PrismaはDBの `NULL` をJSの `null` として返しますが、TypeScriptの型では `avatarUrl?: string`（=undefinedで「無い」を表現）が一般的な書き方なので、ここで表現を揃えています。これを **DTO（Data Transfer Object）変換** と呼びます。

## 5. DB接続の工夫 — Pooler と Direct Connection

サーバーレス環境（Vercel）では、リクエストが来るたびに新しい実行環境が立ち上がる可能性があり、**DBへのコネクションを使い捨てにすると接続数が爆発的に増えて枯渇する**問題があります。これを避けるため2種類の接続先を使い分けています。

| 環境変数 | 用途 | 接続方式 |
| --- | --- | --- |
| `DATABASE_URL` | アプリの通常実行時 | Transaction Pooler（コネクションを使い回す） |
| `DIRECT_URL` | `prisma migrate` 実行時 | Direct Connection（DDL実行に必要な機能をフルで使える） |

```ts
// src/lib/prisma.ts:9
function createPrismaClient() {
  const pool = new Pool({ connectionString, ssl: { rejectUnauthorized: false } });
  const adapter = new PrismaPg(pool);
  return new PrismaClient({ adapter });
}

export const prisma = globalForPrisma.prisma ?? createPrismaClient();
if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = prisma; // 開発時のホットリロードで毎回新規作成されるのを防ぐ
}
```

`globalForPrisma` を使った**シングルトンパターン**がポイントです。開発時、Next.jsはファイル保存ごとにモジュールを再読み込みします。もし毎回 `new PrismaClient()` していたら、コネクションがどんどん増えてしまいます。`globalThis` に保存して再利用することで、これを防いでいます。

## 6. 型共有 — フロントとバックエンドが同じ「契約」を持つ

このプロジェクトはフロントエンドとバックエンドが**同じリポジトリ・同じTypeScriptプロジェクト**にあります。そのため `src/types/index.ts` で定義した型を両方から import でき、**API仕様書を別途メンテナンスしなくても型がズレたらコンパイルエラーになる**という強みがあります。

```ts
// バックエンド（Route Handler）
return NextResponse.json<LoginResponse>({ token, user });

// フロントエンド（apiClient.ts）
const data = await apiFetch<LoginResponse>("/api/auth/login", { ... });
```

両方が `LoginResponse` という同じ型を参照しているため、片方だけ形を変えるとビルドが落ちます。これは「API契約をコードで強制する」シンプルな方法です。

## 7. ひとつのリクエストを最初から最後まで追ってみる

実際に `POST /api/groups/:groupId/expenses`（支出登録）が呼ばれたときの流れを、層を全部通して見てみます。

1. **フロント**: ユーザーが金額・配分を入力して「登録」を押す → `apiClient.ts` の `createExpense()` が `fetch("/api/groups/abc/expenses", { method: "POST", headers: { Authorization: "Bearer xxx" }, body: ... })` を実行
2. **Route Handler起動**: `src/app/api/groups/[groupId]/expenses/route.ts` の `POST` 関数が呼ばれる
3. **認証**: `requireAuthUserId(req)` がヘッダーのトークンを検証 → `userId` を取得（失敗なら即401）
4. **認可**: `assertGroupMember(groupId, userId)` がそのユーザーがグループに属しているか確認（失敗なら403）
5. **バリデーション**: 配分比率の合計が100%か、配分先がメンバーかをコードでチェック（失敗なら400）
6. **DB書き込み**: `prisma.expense.create({ data: { ..., shares: { create: [...] } } })` で `expenses` テーブルと `expense_shares` テーブルに同時book書き込み（nested write）
7. **DTO変換**: Prismaの結果を `ExpenseRecord` 型に変換
8. **レスポンス**: `NextResponse.json(result, { status: 201 })` でフロントに返却
9. **フロント**: 結果を受け取り、フォームをリセットしてトースト表示

この「認証→認可→検証→DB→変換→返却」の8段階が、**このコードベースのすべてのRoute Handlerに共通するテンプレート**です。1つ覚えれば、他のAPIも同じ構造で読めます。

## 8. 用語集（このコードに出てくる言葉）

| 用語 | 一言で | このコードでの例 |
| --- | --- | --- |
| ハッシュ化 | 元に戻せない変換でデータを守る | `bcrypt.hash(password, 10)` |
| JWT | 署名付きの「私は誰か」証明書 | `createToken` / `verifyToken` |
| ステートレス | サーバーがログイン状態を覚えない設計 | JWTをBearerヘッダーで都度送る |
| RBAC | ロールに応じて操作可否を決める認可方式 | `OWNER/ADMIN/MEMBER` |
| ORM | コードでDBを操作する仕組み | Prisma |
| マイグレーション | スキーマ変更の履歴とDB反映 | `prisma/migrations/*` |
| コネクションプーリング | DB接続を使い回して枯渇を防ぐ | `DATABASE_URL`（Pooler） |
| シングルトン | インスタンスを1つだけ作って再利用する設計 | `globalForPrisma.prisma` |
| DTO | 層をまたぐ際のデータの受け渡し専用の形 | `ExpenseRecord` |
| Cascade削除 | 親が消えたら子も自動で消えるDB制約 | `onDelete: Cascade` |
