## 背景 — なぜテストを書くことにしたか

### プロジェクトの現状

sharewallet はこれまで **テストコードが一切なく**、品質担保は次の 2 つに依存していました。

- **手動確認**（ブラウザで画面を操作して動作を見る）
- **TypeScript の型チェック**（コンパイル時の静的解析）

ドキュメント（`docs/18-なぜそう実装したのか.md`）にもある通り、初期フェーズでは仕様変更が多く、テストを大量に書くと **陳腐化コスト** が高いという判断で、意図的にテストを後回しにしていました。

### テストを書き始めるタイミングが来た理由

一方で、アプリの中核機能である **割り勘・精算** が実装され、次のリスクが顕在化してきました。

| リスク | 具体例 |
| --- | --- |
| **金額の誤計算** | 均等割り・カスタム配分で誰がいくら払うべきかが狂う |
| **端数処理のバグ** | 1000 円を 3 人で割ったときの四捨五入で 1 円ずれる |
| **リファクタ時の退行** | `settlement.ts` を直したら、知らないうちに精算結果が変わる |
| **ユーザーの信頼喪失** | お金アプリで「精算額が合わない」は致命的 |

精算ロジックは **純粋関数**（同じ入力なら必ず同じ出力）として切り出されており、DB や HTTP に依存しません。  
テストの **費用対効果が最も高い箇所** なので、ここから着手することにしました。

---

## 目的 — 何を達成したいか

### 主目的

1. **精算計算の正しさを自動で保証する**  
   手動で毎回精算画面を開いて確認する代わりに、コード変更のたびに自動検証する。

2. **テスト基盤の第一歩を踏む**  
   Vitest の導入により、将来 API テスト・CI 連携へ拡張できる土台を作る。

3. **仕様の文書化**  
   テストケース自体が「こういうときこう動くべき」という **実行可能な仕様書** になる。

### 今回あえてやらなかったこと

| やらなかったこと | 理由 |
| --- | --- |
| 全 API ルートの統合テスト | PostgreSQL のテスト DB 準備が必要で、初期コストが高い |
| UI コンポーネントテスト | 画面仕様がまだ変わりやすく、メンテコストが高い |
| Playwright E2E | フロー全体の確認は手動で十分な段階 |
| Zod バリデーション | 別タスク（未実装機能一覧 #8）として切り分け |

**「一番効くところだけ」** に絞るのが今回の方針です。

## 何を実装したか

### 1. Vitest の導入

#### 追加した依存関係

```json
"devDependencies": {
  "vitest": "^4.x"
}
```

Vitest を選んだ理由:

- **高速** — ユニットテスト向きで、起動が軽い
- **TypeScript ネイティブ** — 追加のトランスパイル設定が少ない
- **Jest 互換 API** — `describe` / `it` / `expect` がそのまま使える
- **Next.js プロジェクトとの相性** — Node 環境で `src/lib` を直接テストできる

#### 設定ファイル `vitest.config.ts`

```ts
import path from "path";
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "node",
    include: ["src/**/*.test.ts"],
  },
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"),
    },
  },
});
```

ポイント:

- `environment: "node"` — ブラウザ不要（精算ロジックは DOM に依存しない）
- `include: ["src/**/*.test.ts"]` — `src` 配下の `*.test.ts` を自動検出
- `alias: { "@": "./src" }` — `tsconfig.json` と同じ `@/` パスエイリアスを解決

#### npm スクリプト

| コマンド | 用途 |
| --- | --- |
| `npm test` | CI や PR 前の 1 回実行（`vitest run`） |
| `npm run test:watch` | 開発中にファイル保存のたびに再実行 |

### 2. 精算ロジックのユニットテスト

#### テスト対象

`src/lib/settlement.ts` の `calculateSettlement` 関数。

```ts
export function calculateSettlement(
  members: GroupMember[],
  expenses: ExpenseRecord[]
): SettlementResult
```

この関数がやっていること（概要）:

1. 各支出について、**支払った人に +amount** を加算
2. **配分（shares）または均等割り** で各メンバーから負担分を減算
3. バランスを **四捨五入** して `memberBalances` を生成
4. `minimumCashFlow` で **最少回数の送金** に圧縮した `transactions` を返す

API ルート `GET /api/groups/:groupId/settlement` は DB からデータを取ってきて、この関数に渡しているだけです。  
**ロジックの正しさはここで担保すれば、API 層のバグ以外はカバーできる** のが、ユニットテストを最優先にした理由です。

#### テストファイル

`src/lib/settlement.test.ts`（8 テストケース）

---

### 3. テストケース一覧と意図

| # | テスト名 | 検証していること |
| --- | --- | --- |
| 1 | 支出が 0 件 | 空データでも壊れない（エッジケース） |
| 2 | 2 人・均等割り 3000 円 | 基本ケース：A が払うと A +1500 / B -1500、B→A 1500 円 |
| 3 | 3 人・均等割り 9000 円 | 複数人への送金が正しく生成される |
| 4 | カスタム配分 60/40 | `shares` 指定時の按分計算 |
| 5 | 複数支出の合算 | 2 件の支出を跨いだバランスと精算 |
| 6 | 端数（1000 円 ÷ 3 人） | `Math.round` による四捨五入の挙動を固定 |
| 7 | `shares` が空配列 | 空配列は「配分なし」として均等割りにフォールバック |
| 8 | 複雑な複合シナリオ | 4 人・3 支出で、送金合計 = 負債合計、送金額が正 |

#### ケース 6（端数）について補足

1000 円を 3 人で割ると:

- 理論値: 333.333... 円ずつ
- 四捨五入後: A +667, B -333, C -333
- 送金合計 666 円（理論上の負債 666 円と一致）

**1 円の端数差** は `Math.round` の仕様としてテストで明示的に固定しています。  
将来「端数は支払者に寄せる」などルールを変える場合は、このテストが変更の指針になります。

## テストの書き方 — 採用したパターン

### AAA パターン（Arrange → Act → Assert）

```ts
it("2人で均等割りのとき支払者が相手分を受け取る", () => {
  // Arrange: テストデータの準備
  const members = [member("a", "A"), member("b", "B")];
  const expenses = [expense("a", 3000)];

  // Act: テスト対象の実行
  const result = calculateSettlement(members, expenses);

  // Assert: 期待する振る舞いの検証
  expect(balanceOf(result, "a")).toBe(1500);
  expect(balanceOf(result, "b")).toBe(-1500);
});
```

### ヘルパー関数でノイズを減らす

テスト本体は **「何を検証したいか」** だけが読めるように、データ生成用の小さな関数をファイル内に置いています。

- `member(id, name)` — `GroupMember` の生成
- `expense(memberId, amount, shares?)` — `ExpenseRecord` の生成
- `balanceOf(result, userId)` — 特定ユーザーのバランス取得

### `expect.objectContaining` で必要なフィールドだけ検証

精算トランザクションは `userName` や `userColor` などフィールドが多いため、**金額と送金元・送金先** だけを検証しています。

```ts
expect(result.transactions).toEqual([
  expect.objectContaining({
    fromUserId: "b",
    toUserId: "a",
    amount: 1500,
  }),
]);
```

## よくある質問

### Q. なぜ API ルートではなく `settlement.ts` だけ？

API ルートは **認証・DB・HTTP** に依存するため、テストの準備（モック・テスト DB・トークン生成）が重い。  
`calculateSettlement` は **純粋関数** なので入力を渡すだけで検証でき、**同じバグを最も安く捕まえられる** から。

### Q. 端数 1 円の差はバグでは？

現状の実装は `Math.round` で各メンバーのバランスを丸めているため、理論値と最大 1 円程度ずれることがある。  
これは **既知の仕様** としてテストに固定している。ビジネスルールを変えるならテストも一緒に更新する。

### Q. `npm test` を CI に入れるには？

`.github/workflows/` に workflow を追加し、`npm ci` → `npm test` を実行すればよい。  
統合テストを追加する段階で PostgreSQL service container の設定も検討する。
