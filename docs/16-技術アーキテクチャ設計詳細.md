# 16. 技術・アーキテクチャ・設計 詳細まとめ

このドキュメントは ShareWallet（共有ウォレットアプリ）の **技術スタック / アーキテクチャ / 設計思想** を、面接・コードレビュー・オンボーディングに使える粒度でまとめたものです。
実装状況は [`10-実装状況サマリー.md`](./10-実装状況サマリー.md)、API 仕様は [`07-API仕様書.md`](./07-API仕様書.md)、DB 移行の経緯は [`14-PostgreSQL-Supabase-Vercel実装まとめ.md`](./14-PostgreSQL-Supabase-Vercel実装まとめ.md) を合わせて参照してください。

## 1. プロダクト概要

| 項目 | 内容 |
| --- | --- |
| プロダクト名 | **ShareWallet** |
| 種別 | グループ支出共有 Web アプリ（モバイルファーストの SPA 体験） |
| 主要ドメイン | ユーザー / グループ / メンバー / 支出 / 配分（Share） |
| ターゲット | シェアハウス・サークル・旅行など「複数人で支払いを共有する」場面 |
| 主なユースケース | ログイン → グループ選択 → 支出入力（カテゴリ + 金額 + 配分比率）→ 履歴・ダッシュボード閲覧 |

ビジネス的には「記録」にフォーカスしつつ、将来「精算（割り勘計算）」に拡張しやすいデータ構造を先取りして採用しています（`ExpenseShare` の存在が象徴的）。

## 3. アーキテクチャ全体像

### 3.1 レイヤー構成（論理アーキテクチャ）

```
┌───────────────────────────────────────────────────────────────┐
│                     ブラウザ（Client）                         │
│   React 19 / App Router ページ（"use client"）                │
│   UI state: useState / useEffect, toast, framer-motion        │
│   localStorage: token, selectedGroupId, cached user           │
└───────────────────────┬───────────────────────────────────────┘
                        │  fetch( /api/... , Authorization: Bearer )
                        ▼
┌───────────────────────────────────────────────────────────────┐
│              apiClient.ts（src/lib/apiClient.ts）              │
│   ・トークン / 選択グループ / ユーザーキャッシュの一元管理      │
│   ・apiFetch<T>() で共通化（エラーは ApiClientError）           │
└───────────────────────┬───────────────────────────────────────┘
                        │  HTTP（同一オリジン）
                        ▼
┌───────────────────────────────────────────────────────────────┐
│         Next.js Route Handler（src/app/api/**/route.ts）       │
│   ・requireAuthUserId() / assertGroupMember / assertGroupRole │
│   ・リクエスト検証 → Prisma 呼び出し → DTO 整形 → JSON 返却   │
└───────────────────────┬───────────────────────────────────────┘
                        │  Prisma Client（adapter-pg）
                        ▼
┌───────────────────────────────────────────────────────────────┐
│             PostgreSQL（Supabase, Pooler 経由）                │
│   users / groups / group_members / expenses / expense_shares  │
└───────────────────────────────────────────────────────────────┘
```

責務を「UI」「API クライアント」「Route Handler」「Prisma」「DB」の5層に明示的に分けているのが特徴です。
UI からは **Prisma を直接呼ばず** 必ず `apiClient` → Route Handler を経由するため、
将来 API をサーバ分離する際もフロント側の変更が最小で済むようになっています。

## 4. データモデル設計

### 4.1 ER 概観

```
User ─< GroupMember >─ Group
 │           (role: OWNER|ADMIN|MEMBER, @@unique[userId, groupId])
 │
 ├──< Expense (payer = memberId) ──>─ Group
 │        │
 │        └──< ExpenseShare (percent) >── User (@@unique[expenseId, userId])
 │
 └──< ExpenseShare
```

### 4.2 主要エンティティ（`prisma/schema.prisma`）

| モデル | 主キー | 主要フィールド | 設計ポイント |
| --- | --- | --- | --- |
| `User` | `cuid()` | `email @unique`, `passwordHash`, `color`, `avatarUrl?` | アバターは Data URL（`string?`）で保持し、ストレージ費用を節約 |
| `Group` | `cuid()` | `name`, `color`, `iconUrl?` | 後からアイコンカラム追加したため Route 側にフォールバックあり |
| `GroupMember` | `cuid()` | `role`（enum `GroupRole`）、`@@unique[userId, groupId]` | RBAC の中核。ユニーク制約で二重参加を防止 |
| `Expense` | `cuid()` | `groupId`, `memberId`（＝支払者）, `category`, `amount`, `memo?`, `date` | 支払者と配分を分離しておくことで割り勘計算に拡張可能 |
| `ExpenseShare` | `cuid()` | `expenseId`, `userId`, `percent`, `@@unique[expenseId, userId]` | 1 支出に対する N ユーザーの負担比率（合計 100%） |

- **ネーミング規約**: DB 側は `snake_case`（`@map("password_hash")`）、コード側は `camelCase`。**`@map` で吸収** することで両方のベストプラクティスを両立。
- **削除戦略**: `onDelete: Cascade` を関連テーブルに設定。グループ削除時に `expenses`・`expense_shares`・`group_members` が自動で掃除される。
- **金額**: `Int`（円単位）。`Float` を避けることで丸め誤差を排除。
- **配分比率**: `Float`（%、合計 100 を API 側で検証）。将来「金額配分」にする余地を残している。
- **ID**: 文字列 `cuid()` を採用しログ漏洩・URL 推測のリスクを低減。

### 4.3 スキーマ進化の流れ（マイグレーション履歴）

1. `20260213144041_init` — 初版（SQLite）
2. `20260227150405_core_features` — グループ・支出の本格化
3. `20260313000000_init_postgresql` — **PostgreSQL 初期化**（Supabase 対応）

> 「`dev.db` の SQLite から本番 PostgreSQL に移行」という経緯が残っており、`prisma.config.ts` は `DIRECT_URL` を優先する設計で Pooler と Direct の使い分けを吸収。

## 5. 認証・認可の設計

### 5.1 認証フロー（JWT / Bearer）

```
[Client] POST /api/auth/register
   └── name/email/password → bcrypt.hash(10) → users INSERT

[Client] POST /api/auth/login
   └── email/password
         │
         ▼
   bcrypt.compare → OK なら createToken(userId) で JWT 発行（jose, HS256, 7d）
         │
         ▼
   { token, user } を返却
         │
         ▼
[Client] localStorage["sharewallet_token"] に保存
   以後、apiFetch が Authorization: Bearer を付与
```

- **秘密鍵**: `process.env.JWT_SECRET`（未設定時は `dev-secret-change-in-production`）
- **有効期限**: 7 日。リフレッシュトークンは未導入（シンプルさ優先）
- **保存先**: `localStorage`（XSS を前提にした脅威モデルを認識したうえで採用。HttpOnly Cookie に移行する余地あり）

### 5.2 認可（RBAC）— `src/lib/auth.ts`

ヘルパで権限チェックを一元化し、Route Handler は **「認証 → 権限 → 業務処理」** の 3 段階に整列しています。

| ヘルパ | 役割 |
| --- | --- |
| `getAuthUserId(req)` | `Authorization: Bearer` から userId を取り出す（失敗は `null`） |
| `requireAuthUserId(req)` | 失敗時に `throw "UNAUTHORIZED"`（Route で 401 に変換） |
| `assertGroupMember(groupId, userId)` | グループに所属しているかを確認（`"FORBIDDEN"`） |
| `assertGroupRole(groupId, userId, [OWNER,ADMIN])` | ロール配列に含まれなければ `"FORBIDDEN"` |

ロールは以下の 3 段階（`GroupRole`）：

| ロール | 権限例 |
| --- | --- |
| `OWNER` | グループ削除、OWNER 除外、全設定変更 |
| `ADMIN` | メンバー追加/除外（OWNER 除外は不可）、支出編集 |
| `MEMBER` | 自分の支出の編集・削除、支出登録、閲覧 |

実装の工夫として、**「自分自身の操作」か「他人への操作」かで分岐**し、最後の OWNER は脱退させないガード（`prisma.groupMember.count({ role: OWNER })`）を入れています（`src/app/api/groups/[groupId]/members/[userId]/route.ts`）。

### 5.3 エラーハンドリング規約

Route Handler は業務ロジックで `throw new Error("UNAUTHORIZED" | "FORBIDDEN")` し、最上位の `try/catch` で HTTP ステータスに変換します（401 / 403 / 500）。
メッセージは **日本語 / ユーザー向け** で返却し、フロントは `ApiClientError.message` をそのままトースト表示。

```ts
// 例: src/app/api/groups/[groupId]/expenses/route.ts
} catch (e) {
  if (e instanceof Error && e.message === "UNAUTHORIZED") { return 401; }
  if (e instanceof Error && e.message === "FORBIDDEN")    { return 403; }
  return 500;
}
```

## 6. API 層の設計

### 6.1 エンドポイント一覧

| メソッド | パス | 認証 | 役割 |
| --- | --- | --- | --- |
| POST | `/api/auth/register` | 不要 | 新規登録（bcrypt でハッシュ化） |
| POST | `/api/auth/login` | 不要 | ログイン → JWT 発行 |
| GET/PUT | `/api/users/me` | 必要 | プロフィール取得・更新 |
| GET/POST | `/api/groups` | 必要 | 所属グループ一覧 / 作成（作成者が `OWNER`） |
| GET/PUT/DELETE | `/api/groups/[groupId]` | 必要 | 詳細取得 / 編集（OWNER・ADMIN） / 削除（OWNER のみ） |
| POST | `/api/groups/[groupId]/members` | 必要 | メンバー追加（OWNER・ADMIN） |
| DELETE | `/api/groups/[groupId]/members/[userId]` | 必要 | 除外 / 自分で脱退 |
| GET/POST | `/api/groups/[groupId]/expenses` | 必要 | 支出一覧 / 登録（配分付き） |
| PUT/DELETE | `/api/groups/[groupId]/expenses/[expenseId]` | 必要 | 編集 / 削除（本人 or OWNER・ADMIN） |
| GET | `/api/dashboard/summary` | 必要 | 今月・先月の個人合計、グループ別・カテゴリ別集計 |
| GET | `/api/health` | 不要 | ヘルスチェック |

### 6.2 支出登録の整合性ロジック

`POST /api/groups/:groupId/expenses` は **支払者とシェアの整合性** を 1 トランザクション的に扱います。

1. `assertGroupMember` で所属チェック
2. グループメンバー一覧を取得し `memberIds` 集合を作成
3. `shares` 未指定なら **均等配分**（`100 / members.length`）
4. 合計が `100 ± 0.01`（浮動小数点誤差許容）でなければ 400
5. `shares` 内の `userId` がグループ外、または `percent <= 0` なら 400
6. `payerId = body.memberId ?? userId` がグループメンバーでなければ 400
7. `prisma.expense.create` で `expense` と `expense_shares` を nested write で同時作成

これにより **「メンバーでない人への配分」「合計が 100 でない」** といった業務不整合を DB に書き込ませない設計になっています。

### 6.3 DTO 変換の分離

Prisma モデル → フロント向け DTO（`src/types/index.ts`）の変換は Route 側で明示的に行っています。
たとえば `Expense.member.avatarUrl` は `null` のまま返さず `?? undefined` に統一。
これにより **フロントの型（`?` optional）とシリアライズ表現（null/undefined）の食い違いを吸収** しています。

### 6.4 スキーマ後方互換のフォールバック

`iconUrl` カラムを後から追加した経緯があり、**古い DB / 古いクライアントでもグループ操作が落ちない** ようにフォールバック処理が入っています。

```ts
function isUnknownIconUrlError(e: unknown) {
  return e instanceof Error && (
    e.message.includes("Unknown argument `iconUrl`") ||
    e.message.includes("no such column: groups.icon_url")
  );
}
```

このようなフォールバックは **「本番環境の DB がどの段階か分からない時期」を耐えるための一時的な防波堤** で、マイグレーション定着後に削除候補としてマーク可能です。

## 7. フロント設計

### 7.1 ルーティング / 画面構成（App Router）

| パス | 認証 | 用途 |
| --- | --- | --- |
| `/` | 不要 | スプラッシュ（2.9s で `/home` へ遷移） |
| `/home` | 不要 | ログイン / 新規登録への入口 |
| `/login`, `/register` | 不要 | 認証画面 |
| `/dashboard` | 必要 | 今月集計のホーム |
| `/expense` | 必要 | 支出入力（カテゴリ円グラフ、配分比率入力） |
| `/expense/history` | 必要 | 支出履歴 |
| `/groups/new` | 必要 | グループ作成 |
| `/groups/[groupId]/settings` | 必要 | グループ設定（メンバー管理・編集） |
| `/profile` | 必要 | プロフィール編集・ログアウト |

### 7.2 クライアントサイド状態管理

**グローバルストア（Redux/Zustand など）は未採用**。代わりに以下の 3 つで管理：

1. **ローカル state（`useState`）** — 画面固有の一時入力
2. **サーバー状態** — API から都度 fetch（SWR / React Query は未導入）
3. **ブラウザ永続化（localStorage）** — `apiClient.ts` が単一の入口

| キー | 用途 |
| --- | --- |
| `sharewallet_token` | JWT |
| `sharewallet_user` | `UserProfile` のキャッシュ（BottomNav のアバター即時表示など） |
| `sharewallet_selected_group_id` | 支出入力時の最後に選んだグループ |

`getCachedUser()` でキャッシュを先に表示し、その裏側で `getMe()` を走らせる **Stale-While-Revalidate 風** の UX を `profile/page.tsx` や `BottomNav` で実現しています。

### 7.3 UI パターン / コンポーネント設計

- **Container 分離**: `ScreenContainer`（全画面レイアウト）+ `PageTransition`（Framer Motion）+ `BottomNav`（共通ナビ）で画面の枠が定義される。
- **UI プリミティブ**: `TextInput` / `PrimaryButton` / `ColorPalette` / `GroupAvatar` / `MemberAvatar` / `CategoryIcon` を `components/ui` と `components/icons` に集約。
- **プレゼンテーション駆動**: ロジック（API 呼び出し・バリデーション）は `page.tsx` 側、純粋な表示はプリミティブ側に寄せる。
- **ダークモード**: Tailwind の `dark:` プレフィックスで全コンポーネントに対応済み。
- **アニメーション設計**: スプラッシュ（放射状ゴールドグロー、シマー、パーティクル）・ページ遷移（`opacity + y` のフェード）・ダッシュボードの **数値カウンタアニメーション**（`requestAnimationFrame` + `ease-out` で 900ms）などをマイクロインタラクションとして実装。

### 7.4 エラー・ローディング戦略

- **API エラー**: `ApiClientError(status, message)` を apiClient が一元生成 → 各画面で `toast.error(e.message)`。
- **ローディング**: 画面初期化は `RouteLoading`（スケルトン）で視覚的にブロック。ボタンは `PrimaryButton loading` prop でスピナー表示。
- **非認証時**: `useEffect` 内で `if (!isAuthenticated()) router.replace("/login")`。ガード漏れを防ぐため、認証必須ページの冒頭に同じパターンを必ず置く。

### 7.5 型共有戦略

`src/types/index.ts` にフロント向け DTO を集約し、Route Handler の `NextResponse.json<LoginResponse>(...)` と完全に型を揃えています。**「同一リポジトリ / 同一プロジェクト」** である強みを最大限に利用し、API 契約を OpenAPI 等に頼らずに型だけで担保しています。

## 8. DB 接続設計の工夫（Supabase + pgBouncer）

Supabase の PostgreSQL 運用で問題になりがちな **コネクション枯渇とマイグレーション失敗** を両立させるため、接続文字列を 2 本に分離しています。

| 変数 | 用途 | 接続方式 | 備考 |
| --- | --- | --- | --- |
| `DATABASE_URL` | アプリ実行時 | **Transaction Pooler**（6543） | `?pgbouncer=true&connection_limit=1` を推奨。サーバーレスの大量ファンアウトを捌く |
| `DIRECT_URL` | `prisma migrate` | **Direct Connection**（5432） | 準備済み文・セッション機能を要する DDL 用 |

`prisma.config.ts`：

```ts
export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
    seed: "npx tsx prisma/seed.ts",
  },
  datasource: {
    url: process.env["DIRECT_URL"] ?? process.env["DATABASE_URL"],
  },
});
```

`src/lib/prisma.ts`：

```ts
const pool = new Pool({ connectionString, ssl: { rejectUnauthorized: false } });
const adapter = new PrismaPg(pool);
return new PrismaClient({ adapter });
```

- **Singleton パターン**: 開発時のホットリロードで `PrismaClient` が増殖するのを `globalThis.prisma` で防止。
- **SSL**: Supabase は SSL 必須なので `rejectUnauthorized: false` を設定（証明書検証を一旦許容）。
- **Driver Adapter**: Prisma v7 の新方式で、`pg` + `@prisma/adapter-pg` を組み合わせて純 JS の pg ドライバを使える構成。

## 9. 設計思想・方針（Design Principles）

### 9.1 レイヤリングと責務分離

- 「UI → apiClient → Route Handler → Prisma → DB」のフローを崩さない。
- UI から Prisma を直接参照しない。**型だけ** を `@/types` 経由で共有。
- Route Handler は「認証 → 認可 → バリデーション → I/O → DTO 整形」の5段階で構造化。

### 9.2 堅牢性より単純性を優先

- **Zod 等のバリデータを使わず** 手書きで検証。学習コストとバンドルサイズを優先。
- **SWR/React Query なし**。画面は都度 fetch + `useEffect`。API は小規模なので許容範囲。
- **テストは未導入**（今後の改善候補）。代わりに型と手動動作確認（Supabase の `/api/health` やログイン〜登録〜集計の疎通）で担保。

### 9.3 本番運用を想定した分離

- 環境変数で全てを切替（DB 接続先 / JWT 秘密鍵）。
- マイグレーションを DDL ごとファイルで管理（`prisma/migrations`）し、`migrate deploy` で冪等に適用可能。
- Vercel + Supabase の無料枠で動作可能なよう構成。

### 9.4 データモデリングの方針

- **将来拡張** を見越して `ExpenseShare` を最初から導入（割り勘計算への伏線）。
- **金額は整数（円）**、**配分は `Float`（%）** と用途別に型を分離。
- **Cascade 削除** で整合性を DB に寄せる。

### 9.5 UX 方針

- スプラッシュ〜ホーム〜ログイン〜ダッシュボードの遷移を全てアニメーション化し、「使っていて気持ちいい」 を担保。
- BottomNav を常設し、**モバイルファースト** の親指導線を意識。
- ダッシュボードはアニメーションカウンタ + 先月比 + TOP3 バッジでひと目で状況が分かるよう構成。

## 10. 既知の制約 / 今後の改善候補

| 区分 | 現状 | 将来的な改善案 |
| --- | --- | --- |
| トークン保管 | `localStorage` | HttpOnly / Secure Cookie + CSRF 対策 |
| リフレッシュトークン | 無し（7 日で再ログイン） | アクセス短命 + リフレッシュ長命の 2 本立て |
| バリデーション | 手書き | **Zod** による schema 駆動 + 共通エラー整形 |
| サーバー状態管理 | 都度 fetch | React Query / SWR でキャッシュ・楽観的更新 |
| テスト | なし | Vitest（ユニット）+ Playwright（E2E）+ Prisma のテスト DB |
| 精算ロジック | `ExpenseShare` を保存するのみ | グラフ最適化による「最小送金組み合わせ」計算 |
| 監視 | Vercel ログのみ | Sentry（エラートラッキング）/ Logflare or Supabase logs |
| RBAC | 3 段階（Owner/Admin/Member） | 招待リンク + 一時権限付与、監査ログ |
| 画像 | Data URL を DB に直接保存 | Supabase Storage（外部ストレージ）にオフロード |
| CI/CD | なし | GitHub Actions で `lint` + `build` + `prisma validate` を自動実行 |

## 11. まとめ（アーキテクチャを 1 段落で）

**ShareWallet は「Next.js App Router で UI と API を同居させ、`apiClient` → Route Handler → Prisma → PostgreSQL(Supabase) という単一方向フローに責務を整列させた、フルスタック TypeScript アプリ」です。**
JWT（jose）+ bcryptjs のシンプルな認証、`GroupMember.role` を中心にした 3 段階 RBAC、`Expense` + `ExpenseShare` による「記録と精算を繋ぐ」データモデル、`DATABASE_URL` / `DIRECT_URL` を分離する本番運用前提の DB 構成、Framer Motion と Tailwind によるモバイルファースト UX ── これらが一貫した設計思想（責務分離・単純性優先・本番想定）のもとで統合されています。
