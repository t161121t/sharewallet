# 25. ログイン・登録レート制限実装まとめ

## まず結論（今回できたこと）

- `login` / `register` にIP単位・メールアドレス単位のレート制限を追加した
- PostgreSQLの `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` を使い、カウンタ更新を原子的に行う実装にした(初期実装のレースコンディションをレビューで指摘され修正)
- 期限切れレコードを低確率で削除し、テーブルの無制限な肥大化を防ぐ簡易クリーンアップを入れた
- 本番Supabase DBに新規テーブル`rate_limit_entries`のマイグレーションを適用済み

```bash
npx vitest run   # 36件パス(rateLimit.test.ts 8件を含む)
npx prisma migrate status   # Database schema is up to date!
```

## 背景 — なぜこの変更が必要だったか

`src/app/api/auth/login/route.ts` と `register/route.ts` には、リクエスト回数そのものを制限する仕組みが一切ありませんでした。パスワード照合はbcryptを使っており安全ですが、「何回でも試せる」状態のため、パスワードを総当たりする攻撃や、他サービスから漏れたID/パスワードの組み合わせを試すクレデンシャルスタッフィングに対して無防備でした。

sharewalletは友人・家族間の割り勘アプリで、アカウントが乗っ取られると他メンバーの支出履歴やグループ情報まで閲覧・改ざんされ得るため、issue #22として対応しました。

## 選択肢の比較

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| **A. アプリ内実装(DBで試行回数を記録)(採用)** | 既存Prisma/PostgreSQLに1テーブル追加 | どのホスティング環境でも機能する。閾値を自由に調整できる | テーブル追加・実装・テストが必要 |
| B. Vercel Firewallのレート制限機能 | インフラ設定のみで対応 | 実装コストがほぼゼロ | Vercelに依存し、他環境へ移行すると無効化。メールアドレス単位など細かい制御が難しい |

**Aを採用した理由**: 既に Prisma で DB を保有しており、追加インフラ(Redis等)なしに1テーブル追加するだけで実装できること、また将来のホスティング移行リスクを負わないことから選択しました。

### キーの粒度: IP単位・メールアドレス単位の両方を用意した理由

IP単位だけだと「1つのIPから多数のメールアドレスを試す」攻撃は防げますが、「1つのメールアドレスを複数IP(ボットネット等)から狙う」攻撃は防げません。逆も同様です。両方を独立したキーとして持つことで、どちらの攻撃パターンにも対応できるようにしました。登録エンドポイントは既にメール重複チェックがあるため、IP単位のみとしています(スパムアカウント作成防止が主目的のため)。

---

## 目的

### 主目的

1. ブルートフォース攻撃・クレデンシャルスタッフィングへの耐性をつける
2. 429レスポンス + `Retry-After`ヘッダーでクライアント側にも状況を伝える
3. 追加インフラなしで実現する

### あえてやらなかったこと

| やらなかったこと | 理由 |
| --- | --- |
| Redis等の専用ストア導入 | この規模のアプリではDBで十分。運用コストを増やしたくない |
| CAPTCHA導入 | UXへの影響が大きく、まずは回数制限だけで様子を見る |
| アカウントロックアウト(明示的な凍結) | 誤ロックによるユーザーの締め出しリスクがあり、まずは時間経過で自動解除される方式にとどめる |
| スライディングウィンドウ/トークンバケット方式 | 固定ウィンドウ方式よりデータモデルが複雑になる。今回の規模では固定ウィンドウで十分 |

## 何を実装したか

### 1. `RateLimitEntry`モデル(Prismaスキーマ)

```prisma
model RateLimitEntry {
  id        String   @id @default(cuid())
  key       String   @unique
  count     Int      @default(1)
  expiresAt DateTime @map("expires_at")
  createdAt DateTime @default(now()) @map("created_at")
  @@map("rate_limit_entries")
}
```

`key`は`login:ip:<ip>`や`login:email:<email>`のような文字列。マイグレーションは既存テーブルに影響しない追加のみです。

### 2. `src/lib/rateLimit.ts` — `consumeRateLimit()`

固定ウィンドウ方式で、keyごとの試行回数を数えます。

```ts
const rows = await prisma.$queryRaw<{ count: number; expiresAt: Date }[]>(
  Prisma.sql`
    INSERT INTO "rate_limit_entries" ("id", "key", "count", "expires_at", "created_at")
    VALUES (${randomUUID()}, ${key}, 1, ${newExpiresAt}, now())
    ON CONFLICT ("key") DO UPDATE SET
      "count" = CASE WHEN "rate_limit_entries"."expires_at" <= now() THEN 1 ELSE "rate_limit_entries"."count" + 1 END,
      "expires_at" = CASE WHEN "rate_limit_entries"."expires_at" <= now() THEN ${newExpiresAt} ELSE "rate_limit_entries"."expires_at" END
    RETURNING "count", "expires_at" AS "expiresAt"
  `
);
```

### 3. `login`/`register`ルートへの組み込み

```ts
const IP_LIMIT = { windowMs: 15 * 60 * 1000, max: 20 };
const EMAIL_LIMIT = { windowMs: 15 * 60 * 1000, max: 5 };

const ipCheck = await consumeRateLimit(`login:ip:${ip}`, IP_LIMIT);
if (!ipCheck.allowed) return tooManyRequests(ipCheck.retryAfterSeconds); // 429

const emailCheck = await consumeRateLimit(`login:email:${email}`, EMAIL_LIMIT);
if (!emailCheck.allowed) return tooManyRequests(emailCheck.retryAfterSeconds);
```

## レビューで指摘された点と対応

初回実装(`findUnique` → `upsert`/`update`の2ステップ)には、レビューで4点の指摘を受けました。

| 指摘 | 何が問題だったか | 対応 |
| --- | --- | --- |
| **atomic化(最重要)** | read-then-writeが非atomicなため、ウィンドウ先頭や期限切れ直後に複数リクエストが同時に来ると、全リクエストが「まだ存在しない/期限切れ」と観測し、それぞれcountを1にリセットしてしまう。バーストで制限を大きく突破されうる | `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 1文でDB側の原子操作にまとめた |
| 期限切れレコードの肥大化 | `expiresAt`は判定に使うだけで、レコード自体は削除されない。攻撃者が任意のメール文字列を使い続けるとテーブルが際限なく増える | `consumeRateLimit`内で低確率(1%)に`deleteMany({ expiresAt: { lt: now } })`を実行する簡易クリーンアップを追加 |
| キーの正規化ミスマッチ | レート制限キーは`email.toLowerCase()`していたが、実際の認証(`prisma.user.findUnique`)は大文字小文字を区別してメールを照合していた。大文字小文字違いの別アカウント同士が同じレート制限枠を共有してしまっていた | `toLowerCase()`をやめ、実際の認証と同じ表現(大文字小文字そのまま)をキーに使うよう修正 |
| `x-forwarded-for`の信頼境界が未明示 | 先頭値を無条件でクライアントIPとみなしているが、これは手前のプロキシがこのヘッダーを上書きする構成が前提。そうでない構成ではクライアントが偽装してIP制限を回避できる | コードコメントに前提条件を明記(コード変更ではなく前提の明文化) |

## PR間のマージ順序の調整

このブランチ(#22)は、認証Cookie移行(issue #21・PR #40)が存在する前の`main`から作業を始めていたため、途中まで`login/route.ts`が旧来の`Authorization`ヘッダー/レスポンスボディ`token`返却のままでした。

PR #40を先にマージした後、このブランチを`main`に対して`git rebase`し、`src/app/api/auth/login/route.ts`のコンフリクトを手動解消。最終的に以下の順序になるよう統合しました。

```
レート制限チェック(IP → メール) → パスワード照合 → createToken() → setAuthCookies()
```

自動マージだと`token`フィールドの復活などのコンフリクトが起きやすい箇所だったため、rebase後に改めてビルド・テストを確認してからマージしています。

## よくある質問

### Q. なぜ`findUnique → upsert`ではなく生SQLにしたの？Prismaの通常のAPIだけで書けない？

Prismaの高レベルAPI(`upsert`/`update`)は内部的に複数のSQL文になり、その間にアトミック性を保証できません。1文で完結する`INSERT ... ON CONFLICT DO UPDATE`はPostgreSQL側の行ロックで競合を解決してくれるため、`$queryRaw`で直接書いています。

### Q. カウントがmaxを超えても増え続けるのはバグ？

意図した挙動です。ブロック後も`count`はインクリメントされ続けますが、判定は「`count > max`ならブロック」なので機能的な問題はありません。将来的に「何回攻撃を受けたか」のログとしても使えます。

### Q. `npx prisma migrate deploy`が`FATAL: (ENOTFOUND) tenant/user ... not found`で失敗した

Supabaseの無料プランは一定期間アクセスがないとプロジェクトが自動的に一時停止(pause)されます。この状態でDBに接続しようとすると、接続プーラー(Supavisor)がこのエラーを返します。Supabaseダッシュボードでプロジェクトを再開(Resume)すれば解消します。実際に今回のデプロイでもこれが発生し、プロジェクト再開後に再実行して成功しました。
