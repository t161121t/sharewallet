# 18. なぜそう実装したのか — 設計判断と「Why」のすべて

このドキュメントは、ShareWallet の実装に対して **「なぜそうしたのか」** を一貫して説明することを目的にしています。
「何が」「どう」については [`16-技術アーキテクチャ設計詳細.md`](./16-技術アーキテクチャ設計詳細.md) にまとまっているので、本書は **意思決定（Decision）と理由（Rationale）と代替案（Alternatives）** を中心に、

- **要件定義**（なぜこの機能セットなのか）
- **アーキテクチャ**（なぜこのレイヤ構成なのか）
- **技術選定**（なぜこのスタックなのか）
- **データモデル**（なぜこのテーブル設計なのか）
- **認証・認可**（なぜこの守り方なのか）
- **API**（なぜこのエンドポイント形なのか）
- **フロント**（なぜこの状態管理／UI 構造なのか）
- **実装パターン**（なぜこの 1 行を書いたのか）
- **運用**（なぜこの環境構成なのか）
- **トレードオフ**（なぜ、あえてやらなかったのか）

の 10 軸で掘り下げます。**面接・コードレビュー・後任への引き継ぎ**で「ここなんで？」と聞かれたときに、本書を引いて答えられる粒度を目指しました。

## 0. プロダクトの根本的な「なぜ」

### 0.1 なぜ「グループ支出共有」プロダクトを作ったのか

| 観点 | 内容 |
| --- | --- |
| 背景 | シェアハウス・サークル・旅行・カップルなど、**「立替えと精算」が頻繁に発生する場面** が日常に多い |
| 既存サービスの不満 | 既存アプリ（Splitwise 等）は **多機能だが日本円・日本語 UX に最適化されていない**、SNS 起点のシェアではなく「日々のメモ」感覚で続けたい |
| 解くべき本質 | 「**いま誰がいくら使ったか**」と「**月単位で誰がどれだけ立替えたか**」を **モバイルで 3 タップ以内** に把握できること |
| 採らなかった選択肢 | スプレッドシート（更新コストが高い）／ LINE グループ（流れていく）／ レシート OCR（精度問題と運用負荷） |

→ よって **「カテゴリ + 金額 + 配分」だけで完結する、軽量な記録 + 集計アプリ」** をコアに据え、将来の精算機能拡張の余白だけ最初から構造で確保する方針にしました。

### 0.2 なぜ最初から「精算」をスキーマに織り込んだのか

「記録だけで十分」ならば `Expense` に `amount` と `payerId` だけあれば足ります。
しかし `ExpenseShare`（`expenseId × userId × percent`）を **第 1 リリースから持たせた** のは次の理由です。

1. **データを後から作れない** ：「誰が何 % 負担した」は支出登録時にしか正確に分からない。後から精算機能を足すとき、過去支出が均等割りに固定されてしまうのを避けたかった。
2. **均等割りすら明示する**：未指定なら API 側で `100 / members.length` を `ExpenseShare` として永続化する（`src/app/api/groups/[groupId]/expenses/route.ts`）。これにより **「均等割り」も「カスタム配分」もデータ表現は同じ** になる（読み出しロジックを一本化できる）。
3. **集計クエリを単純化**：`Expense.shares.percent * Expense.amount` で誰の負担分でも算出できる構造。ビジネスロジック側に「もしシェア未設定なら均等で…」のような分岐コードを残さない。

## 1. 要件定義の「なぜ」

### 1.1 機能スコープを「最小限」にした理由

| 含めた機能 | 含めなかった機能（V1） | 理由 |
| --- | --- | --- |
| ユーザー登録・ログイン | OAuth（Google / Apple） | 個人開発で **シークレット管理を最小** にする。コアの体験は email/password で十分検証できる |
| グループ作成・メンバー招待 | チャット機能 | 「精算」の文脈から逸脱する。LINE 等の既存ツールに勝てない領域は意図的に切る |
| 支出登録（カテゴリ + 金額 + 配分） | レシート OCR / 領収書アップロード | OCR 精度・誤登録の責任問題・ストレージコストを **無料運用と相性が悪い** ため除外 |
| ダッシュボード（個人月集計） | 予算機能・通知機能 | 第 1 弾は「振り返り」の体験を完成させ、**先に Push 通知を作ると本質を見誤る** |
| 招待リンク（Token 共有） | メール招待 | SMTP・スパム対策・ドメイン認証が必要で、無料運用が一気に複雑化する |
| 割り勘計算（Settlement API） | 自動引落・送金リンク | 法規制（資金移動業）に踏み込まない。**「いくら送ればいいか」までを責務** にする |

→ **MVP として成立する最小集合 + 拡張の余白** という線引きを意識しています。

### 1.2 なぜ「モバイルファースト Web」なのか（ネイティブにしない理由）

| 軸 | Web（採用） | iOS/Android ネイティブ |
| --- | --- | --- |
| 初期コスト | 1 リポジトリで両プラットフォームに届く | 2 言語 / 2 ストア審査 / 2 課金 SDK |
| 配信 | URL 共有だけで体験開始 | App Store 経由で導入摩擦が大きい |
| 開発速度 | Next.js 1 本で UI〜API〜デプロイ | iOS+Android+API の 3 系統 |
| ストア審査 | 不要 | 招待リンク機能等が原因でリジェクトされる懸念 |

→ **「招待リンクで参加→ブラウザで使い続けられる」** プロダクトとして、Web SPA + モバイルファースト UI が最適と判断しました。
PWA 化の余地は残し（Service Worker は未導入）、**「将来本気度が上がったらネイティブ移植」** という選択肢を閉じない設計にしています。

### 1.3 ロール（OWNER/ADMIN/MEMBER）を 3 段階にした理由

最小なら OWNER と MEMBER の 2 段階でも回りますが、3 段階にした根拠は次の通りです。

- **OWNER の責任を 1 人だけにしない**：OWNER は通常 1 人だが、**本人不在時にメンバー管理が止まる** のを避けるため、信頼できる人を ADMIN として権限委譲できる構造が必要。
- **権限階段を「破壊できない」「拡張できる」「閲覧できる」の 3 段で表現**：実世界のグループ運営に最も馴染む（旅行幹事 + サブ幹事 + 参加者など）。
- **「最後の OWNER は脱退できない」というルールを成り立たせる**：3 段階あれば、OWNER 不在の宙ぶらりんなグループを作らずに済む（[`src/app/api/groups/[groupId]/members/[userId]/route.ts`](../src/app/api/groups/[groupId]/members/[userId]/route.ts)）。

> ❗ MEMBER の権限は **「自分の支出は自分で編集・削除でき、他人の支出は触れない」** という線引きにしています。これは「ログを安易に書き換えられない（=会計の改ざん性を低くする）」という会計アプリとしての最低ラインです。

## 2. アーキテクチャの「なぜ」

### 2.1 なぜ Next.js App Router の 1 リポジトリに UI と API を同居させたのか

選択肢は次の 3 つでした。

1. **モノレポ（Next.js + 別 NestJS / Express）** — フロント / バックを完全分離
2. **BFF 方式（Next.js → 外部 API）** — フロントは Next、API は別サービス
3. **App Router 1 本（採用）** — UI と API を同居

採用理由：

- **型を共有できる**：`@/types/index.ts` を `Route Handler` 側でも `apiClient` 側でも import できる。OpenAPI / tRPC を入れずに **「同一プロジェクト = 同一型」** で API 契約が成立する。
- **デプロイが 1 本**：Vercel に push するだけで UI と API が同時に動く。**個人開発で運用コストをゼロに近づける** ためには 2 サーバの同期は重荷。
- **App Router のサーバ機能（RSC, Route Handler）が成熟**：Pages Router 時代より「サーバとクライアントの境界」がコードで明確（`"use client"`）。**境界を意識した設計** が言語レベルで強制される。
- **将来分離する余地**：それでも UI から Prisma を直接触らず必ず `apiClient → Route Handler → Prisma` の単方向にしているため、API を別サービスに切り出すときも UI 側の変更は最小（後述）。

### 2.2 なぜ 5 層レイヤリング（UI / apiClient / Route Handler / Prisma / DB）を貫いたのか

```
UI ──> apiClient ──> Route Handler ──> Prisma ──> DB
```

「UI から直接 Prisma を呼んでも動く」のに、あえて **5 層を維持** している理由：

| レイヤ境界 | 抽象する責務 | これを破ると起きる悲劇 |
| --- | --- | --- |
| UI ↔ apiClient | URL・トークン保管・JSON シリアライズ | 各画面で `fetch()` が散らばる → 認証ヘッダの付け忘れが起きる |
| apiClient ↔ Route Handler | HTTP（同一オリジン）| クライアントサイドに DB 接続情報が漏れる |
| Route Handler ↔ Prisma | 認可（assertGroupMember 等）| 認可漏れの API が量産される |
| Prisma ↔ DB | SQL の方言・コネクション管理 | 接続の使い回しミスでサーバーレス環境がコネクション枯渇 |

→ **「責任の境界 = ファイルの境界」** にすることで、レビュー時に「この変更はどの層に影響するか」が機械的に判定できます。

### 2.3 なぜ apiClient を「class」ではなく関数群にしたか

`apiClient.ts` は class/インスタンスを使わず **関数 export** にしています（`getMe`, `createExpense`, …）。

- **Tree shaking しやすい**：使った関数だけがバンドルされる
- **Mock しやすい**：将来テストを書くときに `jest.mock("@/lib/apiClient")` で 1 関数だけ差し替えられる
- **Hooks との親和性**：`useEffect(() => { getMe().then(...) }, [])` の素朴な書き方ができる

「単一の `ApiClient` インスタンス」を作ると、シングルトン化のために class やコンテキストを噛ませることになり、**個人開発のスケールに対して過剰** という判断です。

### 2.4 なぜ「Route Handler 内で 5 段階構造」を徹底したのか

すべての Route が **「認証 → 認可 → バリデーション → I/O → DTO 整形」** の同じ並びに整列しています。

```ts
export async function POST(req, { params }) {
  try {
    const userId = await requireAuthUserId(req);          // 1. 認証
    const { groupId } = await params;
    await assertGroupMember(groupId, userId);             // 2. 認可
    const body = await req.json().catch(() => null);      // 3. バリデーション
    if (!body?.category || !body?.amount) return 400;
    const created = await prisma.expense.create({ ... });  // 4. I/O
    const result: ExpenseRecord = { ... };                 // 5. DTO 整形
    return NextResponse.json<ExpenseRecord>(result, { status: 201 });
  } catch (e) {
    if (e?.message === "UNAUTHORIZED") return 401;
    if (e?.message === "FORBIDDEN") return 403;
    return 500;
  }
}
```

→ **同じ形** だからこそ、レビューで「あれ、認可チェック忘れてない？」が **ファイルを開いた瞬間に気付ける**（順序が違ったら異常）。
**コーディング規約をドキュメントで縛らず、構造で縛る** という意図的な選択です。

## 3. 技術選定の「なぜ」

### 3.1 なぜ Next.js 15 / React 19（最新）を選んだのか

- **App Router の Route Handler が安定**：BFF 的に API も持ちやすい。
- **`use client` 境界の明確化**：SSR と CSR の使い分けが言語仕様化されており、「ハイドレーション地獄」を避けられる。
- **Turbopack による高速 HMR**：個人開発の **試行錯誤の速度** に直結する。
- **将来 RSC をフル活用** したくなったときの土台。今は client component 中心だが、`/dashboard` を Server Component 化して **API 経由を介さず DB から直接取る** 改善余地がある。

### 3.2 なぜ jose（JWT）+ bcryptjs を選んだか（NextAuth ではなく）

| 候補 | 採用したか | 理由 |
| --- | --- | --- |
| **jose + bcryptjs**（採用） | ✅ | 依存が薄く、純 JS でサーバーレス互換。仕組みが透明（自分で `createToken / verifyToken` を書ける） |
| NextAuth.js (Auth.js) | ❌ | OAuth プロバイダ前提のフックが多く、シンプルな email/password だけだと逆に冗長。Cookie ベースの設計を強要されるが、まず localStorage で運用を始めたかった |
| `jsonwebtoken` | ❌ | Web Crypto を直接使う `jose` の方がエッジランタイムでも安全に動く |
| `bcrypt`（C++ バインディング） | ❌ | サーバーレス環境でビルドが不安定。`bcryptjs` は遅いが安定して動く |

→ **「フレームワークが決めるのではなく自分で決める」** ことで、認可ロジック（`assertGroupRole`）と一体化させやすくしています。

### 3.3 なぜ Prisma v7 + driver adapter（pg）構成にしたか

- Prisma v7 から **Driver Adapter** が正式採用され、`@prisma/adapter-pg` + `pg` で **JS ネイティブの pg ドライバ** を使える。
- バイナリ依存（旧 query engine）を減らせるため、**サーバーレスのコールドスタート時間が短くなる**。
- **pgBouncer 互換性**が `pg` プールの設計と相性が良い（Supabase の Transaction Pooler 経由でも安定）。
- `src/generated/prisma/client` を `src/generated` 配下に出力して **型を `@/generated` で参照** できるようにしている → 将来 monorepo 化したときも path alias を切り替えるだけ。

### 3.4 なぜ Tailwind CSS 4 + Framer Motion を選んだか

- Tailwind 4 の **`@tailwindcss/postcss` で CSS-in-JS を不要にする**：Atomic CSS のメンテ性 + ダークモード `dark:` プレフィックスが UI ライブラリ層で完結する。
- Framer Motion は **「アニメーションを宣言的に書ける」** ため、複雑なオーケストレーション（スプラッシュの順次フェードなど）が `transition.delay` の数値だけで成り立つ。
- 候補だった **Headless UI / shadcn/ui** は採用していません：理由は **デザインを完全に自前で持ちたかった** ため。Tailwind の primitive を直接組むことで、ブランドカラー（`#c9a227` ゴールド系）と統一感のある UI を最短で表現できる。

### 3.5 なぜ Zod を採用しなかったか

API バリデーションは **手書き** です（`if (!body?.email) ...`）。

| 観点 | 手書き（採用） | Zod |
| --- | --- | --- |
| バンドルサイズ | 0 KB | +13 KB（minified） |
| 学習コスト | なし | スキーマ表現の習熟が必要 |
| 表現力 | 弱い（条件分岐の重複） | 強い（refinement / union） |
| エラーメッセージ整形 | 自前 | 標準で構造化 |

→ **Phase 1 はサイズ重視 + 仕様の流動性を許容**、Phase 4 以降で Zod 化することを `docs/11-未実装機能一覧.md` に明記しています。**「最初から正解を選ばない」** こともデザイン判断です。

### 3.6 なぜ React Query / SWR を入れなかったか

データフェッチは `useEffect` + `useState` の素朴な構成です。

- **画面の数が少ない**（10 画面以下）ため、キャッシュ戦略を仕掛ける旨味より学習・運用コストが上回る。
- **データ鮮度が秒単位で重要ではない**（個人の支出記録）ため、楽観的更新も不要。
- ただし **`apiClient` に `getCachedUser()` という「localStorage キャッシュ + 裏で再取得」** の SWR 風 UX は手書きで入れている（後述）。

将来 React Query を導入するときも `apiClient` の関数群を **そのまま `queryFn` に渡せる** 設計になっており、移行は局所的に済みます。

## 4. データモデルの「なぜ」

### 4.1 なぜ `cuid()` を主キーにしたか

| 候補 | 結論 | 理由 |
| --- | --- | --- |
| `cuid()`（採用） | ✅ | URL に出ても **連番推測** されない。長さがほどよい（25 文字）。タイムスタンプ性質で **B-Tree インデックスが断片化しにくい** |
| `uuid v4` | ❌ | ランダム性が高すぎて B-Tree 挿入のロケーションが散る → インデックスの fragmentation が増える |
| `serial / autoincrement` | ❌ | URL に `/groups/123` のような連番が出ると **総当たり** で件数が推測できる |
| ULID | ❌ | 26 文字でやや長く、エコシステムサポートが Prisma 標準ほど厚くない |

→ Supabase の Postgres 上で運用することを考えると、**乱数性 + ソート性** のバランスが良い `cuid()` を Prisma 標準のまま使うのが最適でした。

### 4.2 なぜ金額を `Int`、配分を `Float` にしたか

```prisma
model Expense       { amount Int }                       // 円単位
model ExpenseShare  { percent Float }                    // %
```

- **金額**: 円単位の整数で持つことで **浮動小数点の丸め誤差** を完全に排除。日本円は基本的に小数点以下を扱わないので合理的。
- **配分**: % は小数（例: 33.33%）を扱うため `Float`。**ただし合計を 100 ± 0.01 で許容** することで浮動小数点の誤差を吸収（[`src/app/api/groups/[groupId]/expenses/route.ts:91`](../src/app/api/groups/[groupId]/expenses/route.ts)）。

→ **「型を揃えない」のではなく「用途別に最適な型を選ぶ」** という判断。会計アプリで `Float` で金額を扱うのは事故の元。

### 4.3 なぜ `@map` で snake_case ↔ camelCase を吸収しているか

```prisma
passwordHash String @map("password_hash")
avatarUrl    String? @map("avatar_url")
```

- **DB は SQL のベストプラクティス（snake_case）** に従いたい：他ツール（Supabase Studio, psql, BI ツール）から見たときに違和感がない。
- **JS/TS は camelCase** に従いたい：ESLint や Prisma Client の自動補完がきれいに動く。
- → Prisma の `@map` で **両方を満たす**。コード側で命名変換ヘルパーを書く必要がない。

### 4.4 なぜ `onDelete: Cascade` を多用したか

`GroupMember`, `Expense`, `ExpenseShare`, `GroupInvitation` のすべてが親に対して Cascade。

- **「グループを削除したら関連データも消える」** はビジネスルール。アプリ層で逐一 transaction を書くと **削除順序のミス** が起きる。
- DB に整合性を寄せることで、**孤児レコード（orphan）を構造的に作れない**。
- アプリ側のコードは `prisma.group.delete()` の 1 行で済む（[`src/app/api/groups/[groupId]/route.ts:174`](../src/app/api/groups/[groupId]/route.ts)）。

ただし **Cascade はテスト時に怖い** という側面もあるので、本番では `OWNER のみ削除可` の認可（`assertGroupRole(... [GroupRole.OWNER])`）で **オペミス耐性** を上げています。

### 4.5 なぜ `GroupMember` に `@@unique([userId, groupId])` を貼ったか

- **二重参加** を DB レベルで防ぐ（同じユーザーが同じグループに 2 回 INSERT されたら整合性が崩れる）。
- **複合主キー** ではなく `id (cuid)` を別途持っている：将来「メンバー固有のメタデータ」（ニックネーム、参加日…）を増やすときに、参照キーが 1 個で済むほうが API/UI の設計が楽。
- **`prisma.groupMember.findUnique({ where: { userId_groupId } })`** が型安全に書ける（[`src/lib/auth.ts:48`](../src/lib/auth.ts)）。

### 4.6 なぜ `Expense.memberId`（支払者）と `ExpenseShare.userId`（負担者）を分離したか

- **「払った人」と「負担すべき人」は別概念**。これを 1 カラムで持つと割り勘が表現できない。
- **N:M を保ったまま 1:N に正規化**：`Expense 1 — N ExpenseShare — N User` という構造で、**1 支出あたりの負担者数や %** を自由に表現できる。
- 結果として精算ロジック（`src/lib/settlement.ts`）が **数行で書ける**：
  - 払った人の balance に `+ amount`
  - 各 share の `userId` の balance に `- amount * percent / 100`
  - 残高の正負で「もらう側 / 払う側」を分け、**Minimum Cash Flow 法** で送金回数を最小化

## 5. 認証・認可の「なぜ」

### 5.1 なぜ JWT を localStorage に置いたか（HttpOnly Cookie じゃなく）

これは **セキュリティ的には物議を醸す選択**で、本書で最も丁寧に「なぜ」を残します。

| 観点 | localStorage（採用） | HttpOnly Cookie |
| --- | --- | --- |
| XSS 耐性 | ❌ JS から読めるので XSS で抜かれる | ✅ JS から読めない |
| CSRF 耐性 | ✅ 自動送信されないので CSRF 不要 | ❌ CSRF 対策（SameSite, トークン）が必須 |
| 実装複雑度 | 低（`localStorage.setItem`） | 中（Set-Cookie 制御 + サーバ側で参照） |
| API クライアントのシンプルさ | 高（fetch に手動でヘッダ付与） | やや低（Cookie 自動送信に依存） |
| クロスドメイン | 容易 | 複雑（CORS + credentials） |

**判断ロジック**：

1. ShareWallet は **同一オリジン（Vercel 配下）** で完結し、外部スクリプトを読み込まない（外部広告 SDK・解析 SDK を入れない）→ **XSS の主因を意図的に断っている**。
2. CSP / SRI を将来入れる前提で、**XSS リスクは「攻撃面が小さい」状態を維持**。
3. CSRF は **SameSite=Lax の Cookie でも完全には防げない** ケースがあり、Bearer 方式は **CSRF を構造的に消せる**。
4. SDK 化（モバイル WebView やデスクトップアプリ）を将来やるとき、**Bearer の方が移植しやすい**。

→ **「攻撃面を絞れる前提で localStorage」**。コミット履歴と CSP の運用ルールが整ったら HttpOnly Cookie へ移行（[11-未実装機能一覧.md](./11-未実装機能一覧.md) に記載）。

### 5.2 なぜ JWT を 7 日有効にしたか

- **個人プロダクトの体験**として、毎週ログインを強要したくない（離脱率が上がる）。
- **リフレッシュトークン未実装** なので、有効期限 = 再ログインまでの猶予と直結する。1 時間にすると UX が崩れ、30 日にすると失効後復旧コスト（ログアウト感の鈍化）が大きい。
- **7 日 = 1 週間の生活サイクル** に揃える：「週末に支出を入れる」習慣のユーザーが切れ目を感じにくい。

→ リフレッシュトークン導入時はアクセス 15 分 / リフレッシュ 30 日が候補（README/16章にも記載）。

### 5.3 なぜ `requireAuthUserId(req)` は `throw` で表現したか

```ts
export async function requireAuthUserId(req: NextRequest): Promise<string> {
  const userId = await getAuthUserId(req);
  if (!userId) throw new Error("UNAUTHORIZED");
  return userId;
}
```

- **早期 return（401 を返す）** だと、Route Handler の本体ロジックが `if/else` の入れ子になって読みにくい。
- **throw** にすることで **try/catch の最外側 1 箇所** にエラーマッピングを集約できる（401/403/500 への分類）。
- **`Error.message` を識別子** に使う Anti-pattern 寄りな書き方ですが、**例外クラスを増やしてもメリットが小さい** 規模感のため、シンプルに割り切っています（将来 `class UnauthorizedError extends Error {}` に置き換える余地は残っている）。

### 5.4 なぜ「最後の OWNER は脱退できない」ガードを入れたか

```ts
if (actor.role === GroupRole.OWNER) {
  const owners = await prisma.groupMember.count({
    where: { groupId, role: GroupRole.OWNER },
  });
  if (owners <= 1) return 400 "最後のOWNERは脱退できません";
}
```

- **OWNER 不在のグループ** が生まれると、招待リンク作成・グループ削除・編集が誰もできなくなる（**zombie group 問題**）。
- DB 制約では表現できない（「OWNER は 1 人以上」という制約は `CHECK` 制約で書きにくい）→ **アプリ層で擁護する** のが最適。
- 将来 ADMIN を OWNER に昇格する API（未実装）を足せば、**OWNER の引き継ぎが UI から完結** する。

### 5.5 なぜ「自分の支出 or 管理者だけが編集できる」ルールにしたか

```ts
if (current.memberId !== userId) {
  await assertGroupRole(groupId, userId, [GroupRole.OWNER, GroupRole.ADMIN]);
}
```

- **会計データの改ざん耐性**：MEMBER が他人の支出を勝手に書き換えると **トラブルの種**。
- **管理者は救済できる**：誤登録の修正は OWNER/ADMIN が担う。
- **シンプルな比較で済む**：登録時に `memberId` を保存してあるので「自分の支出」判定が `===` で書ける。

## 6. API 設計の「なぜ」

### 6.1 なぜ「グループ配下のリソース」を URL に表現したか

```
/api/groups/[groupId]/expenses
/api/groups/[groupId]/members/[userId]
/api/groups/[groupId]/invitations
```

- **「どのグループのリソースか」を URL から型レベルで担保**：Route Handler に `params.groupId` が必ず入るので、認可チェック (`assertGroupMember(groupId, userId)`) を **書き忘れにくい構造**。
- **URL 階層 = 認可境界**：URL を見ただけで「このリソースは groupId に属している」がわかる → API ドキュメントを読まずとも責務が伝わる。
- **REST 風の素直なナビゲーション**：将来 GraphQL や tRPC に移しても、リソース境界が明確なので変換しやすい。

### 6.2 なぜ精算 API（`/api/groups/[groupId]/settlement`）はサーバ側で計算するか

クライアントで `expenses` を取得して JS 側で計算しても表面的には同じ結果が得られます。にもかかわらずサーバで計算する理由：

- **「真実は 1 箇所」原則**：将来「メンバーごとの精算履歴を保存する」拡張をするとき、**サーバ側に計算ロジックがあれば永続化が容易**。
- **クライアント差分を減らす**：iOS/Android アプリを将来出すとき、計算ロジックを再実装したくない。
- **メンバー数が増えても帯域影響を抑える**：N×M の `ExpenseShare` を全部クライアントに送るより、計算済みの送金リスト（最大 `members - 1` 件）を返したほうが軽い。

### 6.3 なぜ DTO 整形を Route Handler 内で手書きしているか

```ts
const result: ExpenseRecord = {
  id: expense.id,
  category: expense.category as ExpenseRecord["category"],
  amount: expense.amount,
  memberId: expense.member.id,
  memberName: expense.member.name,
  memberAvatarUrl: expense.member.avatarUrl ?? undefined,
  ...
};
return NextResponse.json<ExpenseRecord>(result);
```

ORM が返すモデルをそのまま JSON にしないのは：

1. **`null` と `undefined` の差を吸収**：Prisma は欠損値を `null`、TypeScript の `?:` は `undefined`。フロント側で `if (avatarUrl)` の真偽が `null` でも `undefined` でも一致するように、**`?? undefined` で正規化** している。
2. **Prisma の内部表現の揺れを外に漏らさない**：`Decimal`、`Date` などフロントが扱いにくい型を **ISO 文字列・number に変換**。
3. **型 `ExpenseRecord` を書くことで、誤って機密フィールド（`passwordHash`）を返すバグを防ぐ**：`select` し忘れたフィールドが API 経由で漏れない。

### 6.4 なぜ招待リンクは `randomBytes(16).toString("hex")` の Token 形式にしたか

```ts
const token = randomBytes(16).toString("hex"); // 32 文字 hex
```

- **128bit の暗号論的乱数** → 総当たりは現実的に不可能。
- **URL safe（hex のみ）** → エンコードを意識せずどんな経路でも貼れる（LINE、Slack、SMS）。
- **JWT にしなかった理由**：失効管理（revoke）が必要なため、サーバ側に Token テーブル（`GroupInvitation`）を持って **status = ACTIVE/REVOKED** を切り替える方が運用しやすい。JWT は revoke が苦手。
- **`expiresAt` をオプショナルにしている**：永続リンク（社内サークル等）と期限付きリンク（一時旅行）の両方を表現できる。

### 6.5 なぜ「`iconUrl` カラム未対応 DB へのフォールバック」を入れたか

```ts
function isUnknownIconUrlError(e: unknown) {
  return e instanceof Error && (
    e.message.includes("Unknown argument `iconUrl`") ||
    e.message.includes("no such column: groups.icon_url")
  );
}
```

- 開発初期に `iconUrl` カラムを後から追加した。
- **本番 DB のマイグレーションが Vercel デプロイのタイミングと完全には一致しない**（migrate は手動で `prisma migrate deploy` を実行）。
- 「カラムが存在しない瞬間」に **グループ作成・編集が落ちる事故** を起こさないため、エラーをキャッチして `iconUrl` 抜きで再試行している。
- **構造的な技術的負債** ではあるが、**「マイグレーションを適用すれば 1 行削除できる」** 一時的な防波堤として明示的に残している。

→ **「いつ消すかが分かる暫定コード」は、コメントで明示しておけば負債ではなく投資**。

### 6.6 なぜダッシュボード集計をクライアントではなくサーバで作ったか

`/api/dashboard/summary` は「今月・先月の個人支出合計、グループ別 / カテゴリ別」を返します。

- **N+1 を避ける**：複数グループの支出を取って集計すると、クライアントから複数 API を呼ぶ羽目になる。
- **タイムゾーン問題を集約**：`new Date(now.getFullYear(), now.getMonth(), 1)` の月境界判定をサーバ側に寄せる（クライアント時刻に依存しない）。
- **「先月比」のロジックを 1 箇所に**：UI 側で先月 / 今月の 2 リクエストを並列実行する手間を排除。
- **将来 Edge runtime 化** したとき、ユーザーに近い場所で集計が走る余地を残す。

カテゴリ名は **歴史的揺れ**（「交通費」と「交通」など）を `normalizeCategory()` で吸収している（[`src/app/api/dashboard/summary/route.ts:12`](../src/app/api/dashboard/summary/route.ts)）。
これは過去 seed データや旧 UI で別カテゴリ表記が混入した可能性に備えた **データクリーニング** で、本来は migration で値変換すべきだが「**ホットフィックスとして API 層で吸収する**」という選択。

## 7. フロント設計の「なぜ」

### 7.1 なぜグローバル状態管理（Redux/Zustand）を入れなかったか

- **共有が必要な状態が極めて少ない**：本質的にグローバルなのは「ログイン中ユーザー」「選択中グループ ID」だけ → これは **localStorage に置けば十分**。
- **コンポーネント間で props drilling が発生しない**：画面遷移ごとにフルロードするので、親→子で渡したいデータは 1〜2 階層で済む。
- **状態管理ライブラリは「足したら剥がせない」**：最初に入れると将来離れにくいので、本当に必要になるまで先送りする。

→ つまり **「YAGNI（You Aren't Gonna Need It）」を意図的に守っている**。

### 7.2 なぜ localStorage に「token / user / selectedGroupId」を置いたか

| キー | 値 | 理由 |
| --- | --- | --- |
| `sharewallet_token` | JWT | API 呼び出しのたびに取り出すので「同期的にアクセスできる」必要がある |
| `sharewallet_user` | UserProfile | アバターの即時表示。`getMe()` 待ちで「灰色プレースホルダ」を見せると体感品質が落ちる |
| `sharewallet_selected_group_id` | グループ ID | 「最後に支出を入れたグループ」を覚えておくことで、入力フォームの初期選択を再現 |

→ **localStorage の最大の価値は「ページ遷移を跨いで同期的に読める」こと**。React Context や Zustand は「同期だけど SSR と相性が悪い」という弱点があり、Cookie は「サーバ側でしか同期で読めない」。`apiClient.ts` の関数群でアクセスを集約することで、**localStorage 直触りを 1 ファイルに閉じ込めている**。

### 7.3 なぜ「キャッシュ表示 → 裏で再取得」の Stale-While-Revalidate 風 UX を入れたか

```ts
useEffect(() => {
  const cached = getCachedUser();
  if (cached) setUser(cached);          // 即座にキャッシュを表示

  getMe().then((fresh) => {              // 裏で API
    setCachedUser(fresh);
    setUser(fresh);
  });
}, []);
```

- **モバイルの体感品質** は「最初の描画までの時間」で決まる。
- API が遅いネットワーク（LTE / 海外）でも **キャッシュがあれば即座にアバターが出る**。
- 同時に **裏で最新を取りに行く** ので、編集後の反映も自然。
- **SWR / React Query の代用** を最小コードで実現している（依存追加なし）。

### 7.4 なぜページ遷移を Framer Motion でアニメーション化したか

`PageTransition`（`opacity + y` のフェード）+ スプラッシュの放射グロー + ダッシュボードのカウンタアニメーション。

- **CLS（Cumulative Layout Shift）対策**：内容が「ぱっと表示されるのではなく、滑らかに現れる」ことで視線が落ち着き、誤タップが減る。
- **「使っていて気持ちいい」が継続率を上げる**：機能的に Splitwise に勝てなくても、**触感** で差別化。
- **モバイルアプリ風の体験** を Web で再現することで「これ Web だったの？」のサプライズを狙う。

### 7.5 なぜダッシュボードの数値だけ `requestAnimationFrame` で手書きアニメーションしたか

```ts
const tick = (nowMs: number) => {
  const progress = Math.min(1, (nowMs - start) / duration);
  const eased = 1 - Math.pow(1 - progress, 3);
  setAnimatedGroupTotal(Math.round(target * eased));
  if (progress < 1) raf = requestAnimationFrame(tick);
};
```

- **数値カウンタ** は Framer Motion の `motion.span` でも書けるが、**毎フレーム `setState` するため React の再レンダリングを誘発する**。
- 単純な数字 1 つに DOM アニメーション層を被せるのは大袈裟 → `rAF` + `useState` で **十分軽量に表現**。
- Cubic ease-out (`1 - (1-p)^3`) を選んだのは **「最初は速く、最後はゆっくり止まる」** 動きが「金額」のメタファに合うため。

### 7.6 なぜ全画面で BottomNav を共通化したか

- **モバイルアプリ的な親指導線**：Web ながらネイティブアプリの操作感を再現する。
- **常に「ホーム / 入力 / 詳細 / マイページ」が 1 タップで届く** ことで、画面間の迷子をなくす。
- **アバター入りのプロフィールアイコン** を BottomNav に置くことで、**ログイン状態を視覚的に常時確認** できる。

### 7.7 なぜ認証ガードを `middleware.ts` ではなく各画面の `useEffect` に置いたか

```ts
useEffect(() => {
  if (!isAuthenticated()) router.replace("/login");
}, [router]);
```

- **localStorage の値はサーバで読めない**：`middleware.ts` はサーバで動くため、Bearer 方式と相性が悪い。
- **Cookie 方式に移行したら middleware 化** する予定（[11-未実装機能一覧.md](./11-未実装機能一覧.md) に記載）。
- 現状は **「クライアントガード + API 側の `requireAuthUserId` 二重チェック」** で安全性を担保（万が一クライアントを抜けても、API が 401 を返す）。

→ **「セキュリティはクライアントだけで守らない」** が大原則。クライアント側のガードは UX のため、サーバ側のガードがセキュリティのため、という役割分担。

## 8. 実装パターンの「なぜ」

### 8.1 なぜ `prisma` を `globalThis` でシングルトン化したか

```ts
const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined };
export const prisma = globalForPrisma.prisma ?? createPrismaClient();
if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = prisma;
}
```

- **Next.js の HMR（ホットリロード）が PrismaClient を毎回新規生成** する → 接続枯渇の原因。
- **本番では globalThis に持たない**：Vercel の Lambda インスタンスは実行ごとに別プロセスなので、ハマらない。
- 開発時のみ `globalThis` キャッシュ → **「公式パターン」** だが、**なぜそれが必要か** を理解せずコピペすると後々詰まる。

### 8.2 なぜ `params` を `await` で受け取っているか

```ts
{ params }: { params: Promise<{ groupId: string }> }
```

Next.js 15 から **`params` が Promise** になりました（dynamic API の async 化）。

- **動的セグメントの解決を遅延させる** ことで、Edge runtime や RSC の境界を最適化できる。
- 古い書き方 `{ params: { groupId } }` は warning が出る → 早めに新形式に統一した。

### 8.3 なぜ Route Handler に `try/catch` を毎回書いているか

DRY 原則的には共通ラッパー（`withAuth(handler)` 等）を作るのが正攻法ですが、あえて書いていません。

- **try/catch 1 箇所で済む** ので冗長度が低い。
- **共通ラッパーは型を抽象化しすぎる**：`params` の型推論がうまく効かなくなる。
- **どの Route がどんなエラーを返すかが、ファイルを開いた瞬間に見える** → レビュー速度が上がる。

→ 将来 Route が 50 を超えたら Higher-Order Function 化を検討、というラインを引いています。

### 8.4 なぜ `?? undefined` を多用するか

```ts
avatarUrl: user.avatarUrl ?? undefined,
```

- DB は **`null`**、TS の `?:` は **`undefined`** という非対称を吸収。
- JSON シリアライズ時、`null` はキーが残るが `undefined` はキーごと消える → **クライアントの分岐ロジックを `if (user.avatarUrl)` で統一できる**。
- TypeScript の Optional Chain (`user.avatarUrl?.length`) と相性が良い。

→ 「気にせず書いてしまうと nullable が UI 側に染み出す」ので、**API 境界で必ず正規化** している。

### 8.5 なぜ Route Handler で nested write（`prisma.expense.create({ shares: { create: [...] } })`）を使うか

```ts
prisma.expense.create({
  data: {
    ...,
    shares: { create: incomingShares.map((s) => ({ userId: s.userId, percent: s.percent })) },
  },
});
```

- **アプリ層でトランザクションを書かずに済む**：Prisma が内部的に同一トランザクションで実行してくれる。
- **「Expense だけ作られて Share が無い」状態を構造的に防止**：途中で失敗したら全部ロールバック。
- 結果として **コードが宣言的** になり、ビジネスロジックの意図が読みやすい。

→ より複雑な処理（複数モデル横断 + 条件分岐）が必要になったら `prisma.$transaction([...])` に移行する余地あり。

### 8.6 なぜ `Math.abs(percentTotal - 100) > 0.01` で配分合計を判定するか

- **浮動小数点誤差**：`33.33 + 33.33 + 33.34 = 100` のように見えても `99.99999...` になることがある。
- 厳密に `=== 100` だと毎回エラーが返ってしまうため、**0.01% の許容幅** を置く。
- 0.01% 以上のズレは「ユーザーの入力ミス」として 400 を返す。

→ **「数値比較は誤差を前提にする」** という浮動小数点の鉄則。

### 8.7 なぜ Settlement の minimumCashFlow にグリーディアルゴリズムを採用したか

```ts
function minimumCashFlow(balances: MemberBalance[]) {
  const creditors = balances.filter((b) => b.balance > 0).sort((a, b) => b.balance - a.balance);
  const debtors   = balances.filter((b) => b.balance < 0).map(...).sort((a, b) => b.balance - a.balance);
  // 大きい順に詰めていく
}
```

- **真の最適解** は NP-hard（subset sum 問題に帰着）。
- 「最大の債権者と最大の債務者をマッチング」するグリーディは **N - 1 件以内** に収まることが保証される。
- 多くの実用ケースで **真の最小値と一致** または **1 件多いだけ**。
- **計算コストは O(N log N)** でメンバー数が 100 を超えても瞬時。

→ 厳密最適化より **「分かりやすい説明可能性」** と **「軽量さ」** を優先。

## 9. 運用・インフラの「なぜ」

### 9.1 なぜ Supabase を選んだか（PlanetScale / Neon / Render 等ではなく）

| 候補 | 結論 | 理由 |
| --- | --- | --- |
| **Supabase**（採用） | ✅ | Postgres（業界標準）/ 無料枠で本番運用可 / Studio が高機能 / Auth・Storage・RLS まで含めて将来拡張余地が大きい |
| PlanetScale | ❌ | MySQL（ビジネスドメインに対し JOIN 性能の旨味少）/ 無料枠が縮小傾向 |
| Neon | ✅ 候補 | Postgres でブランチ分離が魅力。次回検討候補。 |
| Render PostgreSQL | ❌ | Free tier の自動停止仕様が UX を壊す（コールドスタート時間） |
| 自前 VPS + Postgres | ❌ | 個人開発では運用コスト（バックアップ・SSL 更新）が割に合わない |

→ **「無料で本番運用」+「Postgres 標準」+「将来の機能拡張余地」** の交点。

### 9.2 なぜ `DATABASE_URL`（Pooler）と `DIRECT_URL`（Direct）を分離したか

| 用途 | 接続 | 理由 |
| --- | --- | --- |
| アプリ実行（Vercel の serverless） | `DATABASE_URL`（Transaction Pooler, port 6543） | サーバーレスは **リクエストごとに新コネクション** を貼ろうとする → Postgres の `max_connections`（Free 60）を即枯渇させる。Pooler が短命接続を吸収 |
| Prisma マイグレーション | `DIRECT_URL`（Direct, port 5432） | Pooler は **Transaction-Pooled モードで Prepared Statement やセッション機能を許さない** → DDL が失敗する |

→ **「アプリは Pooler、DDL は Direct」** が Supabase + Prisma の鉄則。
これを `prisma.config.ts` で `process.env["DIRECT_URL"] ?? process.env["DATABASE_URL"]` と書くことで、**「マイグレーション時は強制的に Direct を優先」** している。

### 9.3 なぜ `ssl: { rejectUnauthorized: false }` にしたか

```ts
const pool = new Pool({ connectionString, ssl: { rejectUnauthorized: false } });
```

- Supabase は **SSL 必須**（接続文字列に `sslmode=require` を含む）。
- ただし Vercel の環境では **証明書チェーンの完全検証** が常に通るとは限らない（Lambda の root CA セット差異）。
- **「暗号化はする / 証明書ピン留めはしない」** という妥協点。
- → 本番セキュリティ強化時は CA 証明書をプロジェクトに同梱して `ca:` を指定するのが理想（[16章](./16-技術アーキテクチャ設計詳細.md) の改善候補）。

### 9.4 なぜ Vercel をデプロイ先にしたか

- **GitHub push でゼロ設定デプロイ**：個人開発で CI/CD を組まずに済む。
- **Edge functions / Image optimization** など Next.js とのネイティブ統合。
- **環境変数管理 UI** で Secret を安全に注入。
- **無料枠で 100 GB 帯域** あり、初期トラフィックには十分。
- 競合の Cloudflare Pages も候補だったが、**Prisma + Postgres** の組み合わせは Vercel の方が情報が多く、ハマりにくい。

### 9.5 なぜ生成物（`src/generated/prisma/`）をリポジトリにコミットしたか

通常は `node_modules` 同様 ignore する考え方もありますが、コミット理由：

- **Vercel のビルド時に `prisma generate` を毎回回さなくて済む** → ビルド時間短縮。
- **型差分が PR に出る** → 「DB スキーマ変更を伴う PR で型がどう変わるか」が レビュー時に可視化。
- **CI 不要なシンプル運用**：生成漏れによる本番エラーを構造的に防ぐ。

代償：

- リポジトリサイズが少し大きくなる（許容範囲）。
- マージコンフリクトが発生しやすい → 大規模化したら `.gitattributes` で `merge=ours` を検討。

## 10. トレードオフ — 「なぜ、あえてやらなかったか」

意思決定は「採用したもの」だけでなく「**しなかったもの**」にも理由があります。

| やらなかったこと | 理由 | 将来の判断条件 |
| --- | --- | --- |
| **テスト（Vitest / Playwright）** | 仕様が頻繁に変わる初期は **テストの陳腐化コスト** が大きい。手動 + 型で担保 | 機能が固まり、外部コントリビューターが入るタイミング |
| **Sentry / 監視ツール** | 個人運用で利用者数が少なく、Vercel ログで十分追える | DAU が 100 を超えたとき |
| **Service Worker / PWA** | 招待リンクを開いて即使える Web 性が大事。オフライン需要は薄い | プッシュ通知を真剣に検討する段階で同時導入 |
| **国際化（i18n）** | ターゲットが日本国内で、文言が頻繁に変わる初期は翻訳メンテが過剰 | 海外ユーザーから要望が来た時点で `next-intl` 検討 |
| **Refresh Token** | 7 日 の access token で UX を担保。実装複雑度のわりに守る価値が現状少ない | パスワード変更・即時失効が必要になったら導入 |
| **OAuth ログイン** | 初期は email/password で十分。Google ログインの外部依存を増やしたくない | 個人 → グループ（チーム）利用への展開時 |
| **Zod / Valibot** | バンドルサイズと学習コスト | API が 50 を超えたら schema 駆動が必要に |
| **GraphQL / tRPC** | 1 リポジトリで型共有できているので不要 | API 数が爆発し、UI から自由なクエリが欲しくなったとき |
| **Image Storage（S3 / R2）** | アバターは Data URL で DB に直書き。月数 KB 程度なら無料運用に収まる | 1 画像 100 KB 超を許容 / ユーザー数が万単位 |
| **Pricing / 課金** | 課金導入は **個人情報＋決済の責務** を負う重大な意思決定。MVP 段階では不要 | リテンションが安定したら有料プラン |

## 11. 学び・反省（なぜ「次はこうしたい」か）

| 反省 | なぜそうなったか | 次にどうするか |
| --- | --- | --- |
| `iconUrl` の DB スキーマ後付け → フォールバックが必要に | 初期に Group の見た目要件を詰めきれず、後から色 → アイコンへ拡張 | スキーマレビューに **「最低 3 ヶ月後の UI モック」** を含めて議論する |
| `localStorage` 直アクセスが `apiClient.ts` 以外に少し漏れている（BottomNav） | 「キャッシュは手軽に読みたい」という UX 都合 | 将来は `useCachedUser()` の hook で抽象化 |
| カテゴリ名の歴史的揺れ（"交通費" / "交通"）を API 層で吸収 | 初期 seed と新 UI のズレを許容してしまった | データ移行用 migration を 1 度走らせて吸収コードを消す |
| エラーを `Error.message` で識別 | クラス継承を増やしたくなかった | API が 30 を超えたら `class UnauthorizedError extends Error {}` に置換 |
| グローバル状態管理を入れていない | YAGNI 重視 | リアルタイム同期（WebSocket）を入れる段階で Zustand 検討 |

## 12. まとめ — 設計思想を 3 行で

1. **責務は構造で縛る**：UI → apiClient → Route Handler → Prisma → DB の単方向。各 Route は「認証 → 認可 → バリデーション → I/O → DTO」の同じ並び。
2. **未来の自由度を残す最小実装**：`ExpenseShare` を最初から持たせる、`DATABASE_URL`/`DIRECT_URL` を分離、ロールを 3 段階にする —— **「いま使わない柔軟性」を構造に埋める**。逆に **テスト・Zod・SWR・i18n は YAGNI を貫く**。
3. **モバイル UX は妥協しない**：Stale-While-Revalidate 風キャッシュ、Framer Motion の遷移、`requestAnimationFrame` の数値カウンタ、Bottom Nav の常設 ── 体感品質に関わる部分だけは「手書き」を厭わない。

> ShareWallet の実装にある「**なぜ**」は、ほとんどがこの 3 つから派生しています。本書を読み返したとき、**「これは原則のどれに従っているか」** を逆算できれば、その判断は自信を持って説明できるはずです。

**コードの行単位の説明**（`apiClient` / `auth` / `prisma` / 支出・ダッシュボード・認証・グループ作成など）は [`19-主要コードの詳細解説.md`](./19-主要コードの詳細解説.md) にまとめています。
