# 33. パスワード変更機能実装まとめ

## これは何のドキュメント？

[GitHub issue #29](https://github.com/t161121t/sharewallet/issues/29) で対応した、プロフィール画面からのパスワード変更機能の作業記録です。

---

## まず結論（今回できたこと）

- 現在のパスワードを照合した上で新しいパスワードに変更できる `PUT /api/users/me/password` を新設した
- プロフィール画面にパスワード変更フォーム(現在のパスワード・新しいパスワード・確認用)を追加した
- 新規ルートに11件、registerルートに6件、loginルートに5件(register/loginは既存テストが無かったため新規作成)のユニットテストを追加した

```bash
npx tsc --noEmit   # 型エラーなし
npx vitest run     # Test Files 8 passed / Tests 61 passed
```

---

## 背景 — なぜこの変更が必要だったか

`PUT /api/users/me`(`src/app/api/users/me/route.ts`)は名前・メールアドレス・アイコン色・アバターのみ更新可能で、パスワードは対象外でした。ログイン後にパスワードを変更する手段が一切なく、パスワードを変えたいユーザーは(パスワードリセット機能もまだ無いため)対応する術がありませんでした。issue #29として報告された内容に対応しました。

---

## 選択肢の比較

パスワード変更を既存の`PUT /api/users/me`に統合するか、専用エンドポイントに分けるかの2択がありました。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A. `PUT /api/users/me`に統合 | 既存ルートのbodyに`currentPassword`/`newPassword`を追加で受け付ける | エンドポイントが増えない | パスワード変更だけ「現在のパスワードの照合」という他のプロフィール項目更新には無い前提条件が必要で、条件分岐が複雑になり読みにくくなる |
| **B. 専用エンドポイント`PUT /api/users/me/password`(採用)** | パスワード変更専用のルートを新設する | 「既存リソースを新しい値に置き換える」という`PUT`の意味を保ったまま、ロジックが分離されて読みやすい | エンドポイントが1つ増える |

**Bを採用した理由**: `PUT /api/users/me`(プロフィール更新)と役割・命名の並びを揃えつつ、パスワード変更特有の照合ロジックを混ぜずに済むため。

---

## 目的

### 主目的

1. 現在のパスワードを知っている本人だけが変更できるようにする(なりすまし防止)
2. 既存の認証・パスワードハッシュ化の仕組み(bcrypt)と一貫した実装にする
3. プロフィール画面から迷わず操作できるUIを用意する

### あえてやらなかったこと

| やらなかったこと | 理由 |
| --- | --- |
| パスワードリセット(メール経由) | issue #30として別スコープ。今回は「ログイン中の本人が変更する」ケースのみ |
| パスワード変更後の他セッション・トークンの失効 | 現状JWTは有効期限(7日)まで有効なままになる。セキュリティ強化の余地はあるが、リフレッシュトークン機構(issue #31)と合わせて設計すべき話であり、今回は範囲外とした |
| zodによる本格的なスキーマバリデーション | issue #23の別スコープ。今回は既存の`users/me`ルートと同じ手書きチェックのスタイルに揃えた |

## 何を実装したか

### 1. `PUT /api/users/me/password`(新規)

```ts
const isCurrentPasswordValid = await bcrypt.compare(
  body.currentPassword,
  user.passwordHash
);
if (!isCurrentPasswordValid) {
  return NextResponse.json<ApiError>(
    { error: "現在のパスワードが正しくありません" },
    { status: 401 }
  );
}

const passwordHash = await bcrypt.hash(body.newPassword, 10);
await prisma.user.update({ where: { id: userId }, data: { passwordHash } });
```

新しいパスワードは8文字以上であることをチェックしています(既存コードにこの種の最小文字数ルールが無かったため、今回新たに設定しました)。

### 2. `src/lib/apiClient.ts` — `changePassword()`

```ts
export async function changePassword(
  currentPassword: string,
  newPassword: string
): Promise<{ ok: boolean }> {
  return apiFetch<{ ok: boolean }>("/api/users/me/password", {
    method: "PUT",
    body: JSON.stringify({ currentPassword, newPassword }),
  });
}
```

### 3. `src/app/profile/page.tsx` — パスワード変更フォーム

既存のプロフィール編集セクションと同じ見た目(カード+`TextInput`+`PrimaryButton`)で、現在のパスワード・新しいパスワード・確認用の3つの入力欄と「パスワードを変更する」ボタンを追加しました。クライアント側でも「8文字以上」「確認用と一致」をチェックしてから送信します。

## レビューで指摘された点と対応

このPRのブランチは、`users/me`のエラーハンドリング統一([PR #48](https://github.com/t161121t/sharewallet/pull/48)、issue #20)より前のmainから分岐していたため、新設した`PUT /api/users/me/password`にも同種の問題が持ち込まれていました。マージ作業の中で気づき、修正しました。

| 指摘 | 何が問題だったか | 対応 |
| --- | --- | --- |
| **try/catchで囲まれておらず、`getAuthUserId`(nullチェック方式)を使っていた** | 想定外のDBエラー(接続断など)が発生すると、Next.jsのデフォルトエラーハンドリング(生の500・スタックトレース混じりのレスポンス)にそのまま落ちる。issue #20がまさに直した問題と同じパターンが、新規コードに再度持ち込まれていた | `requireAuthUserId`(投げる方式)+ try/catchに変更し、`groups`/`users/me`など他ルートと同じ`ApiError`形式で返すよう統一 |
| **`currentPassword`が文字列かどうかの型チェックがなかった** | `!body.currentPassword`という真偽値チェックだけでは、`["x"]`のような非空配列が素通りしてしまう(`!["x"]`は`false`)。この状態で`bcrypt.compare`に配列を渡すと例外が発生し、try/catch追加前は生の500になっていた | `typeof body.currentPassword !== "string"`のチェックを追加(`newPassword`側は元々`typeof`チェックがあったが、`currentPassword`側には無かった) |

さらに`/code-review`(2回目、8観点フルレビュー)で5点の指摘を受けました。

| 指摘 | 何が問題だったか | 対応 |
| --- | --- | --- |
| **現在のパスワードの照合にレート制限が無い(最重要)** | このリポジトリでは`login`/`register`が`bcrypt.compare`をIP・メール単位のレート制限([PR #41](https://github.com/t161121t/sharewallet/pull/41))で保護する慣習が確立しているが、このルートには同種の保護が無かった。認証Cookieを(XSSのセッションライディングや共有端末経由で)盗んだ攻撃者は、本人のパスワードを知らなくても、レスポンスの401/成功の違いを見ながら無制限に現在のパスワードを総当たりできてしまう | `consumeRateLimit`を導入し、`password-change:user:${userId}`(本人単位、15分に5回まで)でレート制限。IPではなくuserIdでキーを切っているのは、攻撃者はCookieさえあればどのIPからでも試行できるため |
| 新しいパスワードが空白のみでも通ってしまう | `body.newPassword.length < MIN_PASSWORD_LENGTH`は長さだけを見ており、`"        "`(半角スペース8個)のような空白のみの文字列も8文字としてカウントされ、そのままハッシュ化・保存されてしまう | `body.newPassword.trim().length < MIN_PASSWORD_LENGTH`に変更(クライアント側の`profile/page.tsx`も同様に修正) |
| `MIN_PASSWORD_LENGTH`が`route.ts`と`profile/page.tsx`の2箇所に独立して重複定義されていた | 将来最小文字数のルールを変更する際、片方だけ直し忘れるとクライアント側とサーバー側の検証基準がズレる(UIでは通るのにAPIでは弾かれる、あるいはその逆) | `src/lib/validation.ts`に`MIN_PASSWORD_LENGTH`を切り出し、両方から`import`する形に統一 |
| パスワード変更中も3つの入力欄が編集可能なままだった | `changingPassword`中に`TextInput`を無効化する仕組みが無く(`TextInput`コンポーネント自体に`disabled` propが存在しなかった)、リクエスト送信中にユーザーが入力し直すと、成功時に`setCurrentPassword("")`等で無警告のまま上書き・消去されてしまう | `TextInput`に`disabled` propを追加し、3つの入力欄すべてに`disabled={changingPassword}`を指定 |
| `prisma.user.findUnique`が`passwordHash`だけで十分なのに全カラムを取得していた | 名前・メール・アバター等の不要なカラムまで毎回取得しており、将来`User`に機微なカラムが追加された場合にこのハンドラが意図せずそれを取得し始めるリスクもある | `select: { passwordHash: true }`を指定し、必要な列だけ取得するよう変更 |

さらに3回目のレビューで2点の指摘を受けました。1件は前回の修正(空白のみパスワード対策)が原因で作り込んでしまった新しいバグでした。

| 指摘 | 何が問題だったか | 対応 |
| --- | --- | --- |
| **検証(trim後)とハッシュ化(trim前)で異なる値を使っていた(最重要・自己回帰バグ)** | 前回の修正で`body.newPassword.trim().length < MIN_PASSWORD_LENGTH`と検証だけtrimするようにしたが、実際に`bcrypt.hash()`に渡していたのは`body.newPassword`(trimしていない元の値)のままだった。例えば末尾に半角スペースが入った新パスワードを送ると、検証は通るが保存されるハッシュはスペース込みの値になり、次回ログイン時にスペース無しで入力すると一致せず、パスワード変更した本人が直後にログインできなくなる(意図せぬロックアウト) | `const newPassword = body.newPassword.trim();`を1つ作り、検証・ハッシュ化の両方でこの同じ変数を使うように統一。テストも追加(末尾に空白がある入力で、trim後の値が`bcrypt.hash`に渡ることを確認) |
| `MIN_PASSWORD_LENGTH`が「共有」と謳いつつ`register`ルートには適用されていなかった | `src/lib/validation.ts`のコメントで「クライアントとサーバーで共有する」と書きながら、実際には`password/route.ts`と`profile/page.tsx`にしか配線されておらず、`register/route.ts`にはパスワード長のチェックが一切無かった。1文字のパスワードで新規登録でき、後からそのパスワードに「変更」しようとすると最小文字数エラーになるという矛盾した挙動になっていた | `register/route.ts`(サーバー側)と`register/page.tsx`(クライアント側)にも同じ`MIN_PASSWORD_LENGTH`を使った検証を追加。あわせて`register`側も検証とハッシュ化を同じtrim後の値に統一(同じ自己回帰バグを新規に作り込まないよう注意)。`register/route.ts`に既存テストが無かったため、新規に`route.test.ts`を作成(6件) |

さらに4回目のレビューで5点の指摘を受けました。うち1件は、前回・前々回の修正(trimによる不一致解消)が`register`/`password/route.ts`側だけに閉じており、**`login`側を直し忘れていた**ことによる、影響範囲の広い回帰バグでした。

| 指摘 | 何が問題だったか | 対応 |
| --- | --- | --- |
| **`login`が生の(trimしていない)パスワードで照合していた(最重要・影響範囲が最も広い回帰バグ)** | `register`と`password/route.ts`は新しいパスワードをtrim後にハッシュ化するよう直したが、`login/route.ts`の`bcrypt.compare(body.password, ...)`はtrimしないままだった。末尾に空白のあるパスワードで登録/変更すると、ハッシュはtrim後の値で保存されるのに、ログイン時は生の値(空白込み)で照合するため**恒久的にログインできなくなる**。この不整合はPR内の3ファイル(login/register/password)にまたがっており、1箇所だけ見ていては気づけない性質の問題だった | `src/lib/validation.ts`に`normalizePassword()`(trimのラッパー)を追加し、`login`/`register`/`password-change`の全てのbcrypt呼び出し(照合・ハッシュ化どちらも)で必ずこの関数を通すよう統一。`login`に専用テストを新規作成(5件、末尾空白ケース含む) |
| `password/route.ts`内で`currentPassword`が未正規化・`newPassword`のみ正規化という非対称があった | `newPassword`側だけ`trim()`しており、照合対象の`currentPassword`は生の値のままだった。trim後の値でハッシュ化された(過去に変更した)パスワードを、末尾に空白付きで再入力すると照合に失敗し、本人なのに「現在のパスワードが正しくありません」になる | `currentPassword`/`newPassword`とも`normalizePassword()`を通すよう統一 |
| `tooManyRequests()`が`login`/`register`/`password`の3ファイルに全く同じ内容でコピペされていた | 429レスポンスの形式やメッセージを変える際、3箇所を漏れなく直す必要があり、1箇所直し忘れるとレスポンス形式がルート間でバラバラになるリスクがあった | `src/lib/rateLimit.ts`に`tooManyRequestsResponse()`として集約し、3ファイルから`import`する形に統一 |
| trim検証ロジック(コメント含む)が複数ファイルに分散していた | `MIN_PASSWORD_LENGTH`と組み合わせた「trimしてから長さを見る」というロジックが`register`/`password`双方に別々に書かれており、将来ルールを変える際に同じtrim不一致バグを再び作り込むリスクがあった | `src/lib/validation.ts`に`normalizePassword()`/`isPasswordLongEnough()`を追加し、各ルートはこれらを呼ぶだけにした |

セッション/トークンの失効については、「目的」セクションに記載の通り引き続き意図的な対象外(issue #31待ち)です。

## よくある質問

### Q. なぜ `PUT` にしたの？`POST` じゃダメ？

「既存のリソース(パスワード)を新しい値に置き換える」操作なので、意味的にはPUTが自然だと判断しました。`PUT /api/users/me`(プロフィール更新)と並びも揃っています。

### Q. なぜ8文字にしたの？

既存コードには最小文字数のルールが全く無かったため、一般的な最低ラインとして8文字を新たに設定しました。より厳密な強度要件(記号必須など)は今回は入れていません。

### Q. パスワードを変更したら、ログイン中の他のデバイスは即ログアウトされる？

されません。現状のJWTは有効期限(7日)まで有効なままです。これはissue #31(リフレッシュトークン機構)と合わせて設計すべき話として、今回は対象外としました。
