# 30. Prisma マイグレーション履歴の整理まとめ

## これは何のドキュメント？

[GitHub issue #26](https://github.com/t161121t/sharewallet/issues/26) への対応記録です。SQLite→PostgreSQL移行時に残った「意図的なno-opマイグレーション」2つについて、履歴を書き換える(squash)か、事情をドキュメント化するかを検討し、後者を選んだ経緯をまとめています。

---

## まず結論（今回できたこと）

- マイグレーションファイル自体は**一切変更していない**
- `prisma/migrations/README.md`(新規)に、2つのno-opマイグレーションの位置づけと、それが存在する理由を明記した
- `docs/30-Prismaマイグレーション履歴の整理まとめ.md`(本ドキュメント)として作業の背景を記録した

```bash
npx tsc --noEmit   # 型エラーなし(そもそもこの変更はコードに触れていない)
npx vitest run     # 全件パス
```

---

## 背景 — なぜこの整理が必要だったか

`prisma/migrations/20260213144041_init` と `prisma/migrations/20260227150405_core_features` の中身は、以下のようなno-opコメントのみになっています。

```sql
-- This migration was superseded by the PostgreSQL baseline migration.
-- Kept as an intentional no-op to preserve migration history ordering.
```

これはSQLite→Postgres移行時に「履歴の順序維持のため意図的に残した」ものですが、新規に参加する開発者や新規環境構築時にこの履歴を上から順に読むと、「このマイグレーション、何もしていないけど何のためにあるんだろう?」と混乱しやすい状態でした。

---

## 選択肢の比較

issueでは2つの対応方針が提案されていました。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A. 履歴をsquashする | `20260213144041_init` と `20260227150405_core_features` を削除し、`20260313000000_init_postgresql` を正式なベースラインとして履歴を作り直す | 履歴がすっきりする。無意味なファイルが減る | **本番DBの`_prisma_migrations`テーブルには、この2つが「適用済み」として名前付きで記録されている。** ファイル名を変更・削除すると、`prisma migrate deploy`が「記録されているはずのマイグレーションがリポジトリに存在しない」状態を検出し、次回以降のデプロイでエラーになったり、意図せず再適用を試みたりするリスクがある |
| **B. ドキュメントを追加する(採用)** | ファイルには一切手を触れず、`prisma/migrations/README.md`で経緯を説明する | 本番DBの適用履歴と完全に整合したまま、読む人の混乱だけを解消できる。作業がノーリスク | 「不要なファイルそのもの」は残り続ける |

**Bを採用した理由**: このリポジトリでは既に本番のSupabase DBが稼働しており、そのDBの`_prisma_migrations`テーブルはSQLite時代のマイグレーション名を含めて履歴を記録しています。squash(A)は「見た目のきれいさ」と引き換えに「本番マイグレーション管理の整合性」という、取り返しのつきにくいリスクを負うことになります。issue自身も「整理が難しい場合はドキュメントを追加する」という代替案を用意していたため、実害のないBを選びました。

---

## 目的

### 主目的

1. 新規参加者・新規環境構築時に、no-opマイグレーションの意味がその場でわかるようにする
2. 本番DBのマイグレーション適用履歴には一切手を加えない

### あえてやらなかったこと

| やらなかったこと | 理由 |
| --- | --- |
| マイグレーションファイルのリネーム・削除・squash | 本番DBの適用履歴とのズレによる`prisma migrate deploy`failureリスクがあるため |
| no-opファイルの中身をより詳しい説明に書き換える | ファイルの中身自体を変更する行為も、ハッシュ検証等に影響しうるため触れないほうが安全。説明はREADME側に集約した |

---

## 何を実装したか

### `prisma/migrations/README.md`(新規)

各マイグレーションの位置づけを表にまとめ、`20260313000000_init_postgresql`が実質的なベースラインであること、2つのno-opは本番DBの適用履歴と一致させるためにそのまま残す必要があることを明記しました。

## よくある質問

### Q. 将来的にsquashできるタイミングはあるの？

理論上は、本番DBを一度クリーンな状態から作り直す(=新しいプロジェクトとして再構築する)タイミングであれば、`_prisma_migrations`の記録もリセットされるため安全にsquashできます。ただし、そのようなタイミングは頻繁には来ないため、今回は「実害のないドキュメント化」を優先しました。

### Q. no-opファイルの中身を書き換えて、もっと詳しい説明にすればいいのでは？

Prismaはマイグレーションファイルの内容に対してチェックサムを保持していないため実害はない見込みですが、「適用済みマイグレーションの中身は変更しない」という原則を一貫させる方が安全だと判断し、説明は`README.md`側にのみ書きました。
